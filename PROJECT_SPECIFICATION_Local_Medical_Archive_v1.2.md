### Изменения относительно v1.1

Уточнены основания требований: обязательны медицинские PDF с текстовым слоем, TXT и Markdown; семь форматов исходного задания больше не являются обязанностью медицинского варианта. Python, ChromaDB, `rank_bm25` и четыре выбранных имени MCP-инструментов остаются решениями проекта. Алгоритмы BM25/RRF/Corrective RAG, Ollama, Docker Compose, настоящий MCP и корпус не менее 512000 байт сохраняются.

MCP становится контролируемым выходом общего RAG: ответы и найденные фрагменты проходят общую с ручной консультацией проверку правилами и локальной LLM. Наружу выдаются очищенные данные и непрозрачные ссылки `responseRef`/`S1`; пути, названия, внутренние ID и трассы остаются локально. При сбое проверки исходные данные не выдаются. Проверки охватывают приватность и сохранение полезного медицинского содержания, а не только точность поиска.

Это принятие рекомендаций конспекта как проектных решений, не объявление новых дословных требований преподавателя. MVP не расширяется OCR, изображениями, диагностикой, многопользовательским режимом или внешними AI API. Ручной просмотр и точный review hash личного экспорта сохраняются. Защита 28 сентября 2026 помечена как перенесённая, новая дата не подтверждена. Полная карта решений — [docs/CONSULTATION_CHANGES.md](docs/CONSULTATION_CHANGES.md).

# 1. Цель проекта

Разработать локальное однопользовательское приложение для хранения, каталогизации, структурирования, поиска и анализа медицинских документов с использованием локальной большой языковой модели и Corrective RAG.

Система должна:

- хранить медицинские документы локально;
- поддерживать загрузку PDF с текстовым слоем, текстовых транскриптов приёмов и текстовых заметок;
- автоматически извлекать из документов структурированные медицинские факты;
- формировать медицинскую временную шкалу;
- обеспечивать обычный поиск и AI-поиск по архиву;
- сохранять provenance для AI-извлечённых фактов;
- позволять пользователю корректировать AI-извлечения с сохранением истории;
- готовить деперсонализированный текстовый пакет для ручной передачи внешней frontier LLM;
- не отправлять личный архив во внешние AI API; выдача синтетического корпуса подключённому MCP-хосту регулируется отдельной границей §16 и §25;
- предоставлять настоящий MCP-интерфейс общего Corrective RAG с проверенной и очищенной выдачей синтетического корпуса внешнему хост-агенту.

Приложение проектируется как полноценный MVP будущего персонального медицинского архива, а не как демонстрация отдельных AI-функций.

# 2. Основные принципы

## 2.1 Local-first

Оригиналы, текст, факты, индексы и история остаются локально. Все модели, обрабатывающие архив, вызываются локально. В runtime нет SDK внешнего LLM API, шлюза к внешнему LLM-провайдеру и его ключей. Локальный сетевой nginx ingress/host-Ollama proxy не является таким AI-шлюзом и допускается для loopback-доступа и ограничения сети. Первичная загрузка образов/весов отделена от работы с медицинскими данными; установка без заранее доступных зависимостей не обещается полностью offline.

## 2.2 Human-in-the-loop

AI-извлечения — предложения модели. Пользователь проверяет источник и исправляет результат с историей. Неизвестное значение не выдумывается; предположение не становится установленным диагнозом, назначение не доказывает фактический приём лекарства, отрицание сохраняет смысл.

## 2.3 Provenance

У AI-факта должны быть документ и исходный фрагмент, при применимости — страница/позиция/chunk. Если подтверждение не найдено, результат не становится автоматически подтверждённым фактом: сохраняется как кандидат с предупреждением либо отклоняется. Ручные исправления маркируются отдельно от утверждений источника.

## 2.4 Структурированные данные и RAG

Timeline, фильтры и числовые представления используют структурированные данные. Свободный вопрос Ask Archive и MCP `ask_question` используют полный Corrective RAG. Универсальный агент, самостоятельно генерирующий SQL, не нужен для MVP.

Поправка пользователя не переписывает PDF. При ответе различаются исходный документ и пользовательская коррекция; исходная цитата не выдаётся за доказательство исправленного пользователем числа.

## 2.5 Контролируемый ручной экспорт

Система минимизирует и деперсонализирует контекст, показывает точный preview и предупреждения. Пользователь проверяет, копирует или сохраняет Markdown и самостоятельно отправляет его дальше. Кнопки Send и автоматической отправки личной консультации нет. Отдельный MCP-канал отвечает подключённому хост-агенту только по синтетическому корпусу после автоматической privacy-проверки; такой ответ является передачей данных хосту и не требует ручного Copy.

## 2.6 Воспроизводимость

Сохраняются версии модели, промпта, схемы и обработки. Намерения, реализация и выполненные проверки различаются. Нельзя заранее объявлять функцию реализованной, придумывать качество или восстанавливать несуществовавшую историю Git/REPORT.

# 4. Пользователь

MVP рассчитан на одного локального пользователя.

Авторизация в первой версии не требуется.

# 5. Основные пользовательские сценарии

Числа и медицинские примеры ниже иллюстративны и относятся к синтетическим данным, а не к истории пользователя.

## UC-01. Загрузка PDF

1. Пользователь открывает Archive.
2. Нажимает Upload.
3. Выбирает PDF с текстовым слоем.
4. Backend сохраняет оригинальный файл.
5. Создаётся Document.
6. Из PDF извлекается текст.
7. Документ отправляется на локальную AI-обработку.
8. Создаются:
   - summary;
   - document type;
   - tags;
   - extracted facts;
   - chunks;
   - embeddings.
9. Документ становится доступен в Archive, Timeline и поиске.

## UC-02. Добавление транскрипта приёма

Пользователь создаёт текстовую запись типа `VISIT_TRANSCRIPT` и вставляет текст транскрипта.

Система обрабатывает его как медицинский документ:

- summary;
- specialty;
- diagnoses;
- symptoms;
- medications;
- recommendations;
- timeline event при известной дате; иначе событие остаётся без точной даты.

## UC-03. Создание личной заметки

Пользователь создаёт текстовую заметку, указывает:

- title;
- date;
- tags;
- content.

Заметка индексируется вместе с другими документами.

## UC-04. Просмотр документа

Страница документа отображает:

- название;
- тип;
- дату;
- статус обработки;
- tags;
- summary;
- исходный текст / ссылку на PDF;
- извлечённые факты;
- provenance;
- историю изменений.

## UC-05. Исправление AI-факта

Пример:

AI извлёк:

`LDL = 4.7 mmol/L`

Пользователь меняет значение на:

`LDL = 4.1 mmol/L`

Система:

- сохраняет исходное AI-значение;
- сохраняет новое значение;
- создаёт запись AuditEvent;
- показывает исправленное значение как актуальное.

## UC-06. Просмотр Timeline

Пользователь открывает Timeline и видит события в хронологическом порядке.

Пример:

```text
2025-03-12
Blood test
LDL 4.1 mmol/L

2025-03-27
Cardiology visit
Recommendation: ...

2025-04-01
Medication started
Atorvastatin 20 mg
```

Каждый элемент Timeline должен вести к источнику.

## UC-07. Обычный поиск

Пользователь вводит:

`тахикардия`

Система выполняет full-text search по индексируемому тексту.

Дополнительно доступны фильтры:

- date from / to;
- document type;
- tags;
- processing status.

## UC-08. Ask Archive

Пользователь спрашивает:

> Когда впервые упоминался повышенный LDL и какие рекомендации были даны?

Система запускает Corrective RAG:

1. rewrite;
2. hybrid retrieval;
3. grading;
4. при необходимости broaden + retry;
5. generation;
6. ответ + sources.

## UC-09. Подготовка внешней консультации

Пользователь вводит вопрос:

> Подготовь данные для внешней консультации о причинах роста ALT.

Система:

1. локально выбирает релевантный контекст;
2. минимизирует объём данных;
3. удаляет или заменяет очевидные персональные идентификаторы;
4. локальная LLM выполняет дополнительный privacy pass;
5. генерирует external consultation package;
6. показывает preview;
7. показывает privacy warnings;
8. после ручного подтверждения текущего текста позволяет Copy / Export Markdown.

Приложение не выполняет сетевую отправку.

- У `ExternalConsultation` дополнительно сохраняются локальные source refs, версии генерации, статус `DRAFT/NEEDS_REVIEW/REVIEWED`, hash содержимого и hash просмотренной версии. Внешний Markdown не содержит внутренние refs/пути или таблицу замен.
- Схема логическая. Окончательные имена полей и миграции фиксируются в ARCHITECTURE и коде, не считаются уже созданными.

<a id="section-8"></a>

# 8. AI extraction schema

Локальная LLM должна возвращать структурированный JSON.

Пример:

```json
{
  "documentType": "LAB_REPORT",
  "documentDate": "2025-03-12",
  "specialty": null,
  "summary": "Routine blood test...",
  "tags": ["blood-test", "lipids"],
  "facts": [
    {
      "type": "LAB_RESULT",
      "name": "LDL",
      "valueNumber": 4.1,
      "valueText": null,
      "unit": "mmol/L",
      "eventDate": "2025-03-12",
      "confidence": 0.96,
      "provenance": {
        "page": 2,
        "sourceText": "LDL cholesterol 4.1 mmol/L"
      }
    }
  ]
}
```

Требования:

- JSON должен валидироваться;
- неизвестные значения не должны выдумываться;
- неподтверждённые поля должны быть `null`;
- источник должен сохраняться, если он доступен;
- AI extraction не модифицирует оригинальный документ.

Цитата проверяется на наличие в соответствующей версии источника. Валидный JSON сам по себе не подтверждает факт. При невалидном ответе допускается ограниченный технический повтор, затем понятная ошибка; этот лимит отделён от двух corrective-повторов RAG.

При повторной обработке сохраняется новый результат модели, но не затираются проверенные ручные исправления. Конфликт решается пользователем без сложного автоматического слияния. Показанное в JSON поле `confidence` иллюстрирует возможный ответ модели, не доказанную точность.

<a id="section-9"></a>

# 9. История и версионирование

История должна фиксировать минимум:

- загрузку документа;
- изменение metadata;
- завершение AI extraction;
- correction extracted fact;
- reprocessing;
- deletion;
- restoration.

Для исправляемых AI-фактов обязательно сохранять исходное AI-значение.

Оригинальный файл считается immutable.

Для изменяемых заметок/транскриптов сохраняется версия текста. Удалённые документы исключаются из обычного поиска, RAG, timeline и новых консультаций; восстановление возвращает их после актуализации индекса. BM25 и Chroma обновляются согласованно, повторная индексация не создаёт дубли.

Старые консультации — локальные снимки, не автоматически актуальный контекст после правки источника. В MVP soft delete не означает физическое стирание; срок 30 дней из варианта 5 не переносится. Для переиндексируемых записей либо исключается устаревшая версия, либо явно показывается её состояние.

NestJS владеет прикладными сущностями и открытым REST API; Python — обработкой и общим RAG engine. UI не подключается к БД и файловой системе напрямую.

Локальный кабинет получает полные источники. Перед выходом из MCP общий privacy-компонент проверяет ответ и каждый фрагмент; внешняя схема собирается по разрешённому списку полей. Источник обозначается как `S1` внутри свежего `responseRef`, связь с реальным документом остаётся локально. Тот же компонент правил и локальной LLM применяется при подготовке ручной консультации, у которой дополнительно обязательны preview и подтверждение hash.

<a id="section-13"></a>

# 13. RAG indexing

RAG corpus индексируется отдельно от PostgreSQL.

## Vector storage

ChromaDB in-process.

## Sparse retrieval

BM25 через `rank_bm25`.

## Hybrid retrieval

Используется:

```text
BM25 results
+
Vector results
        ↓
Reciprocal Rank Fusion
        ↓
Combined ranking
```

В реализации выбран LangChain `EnsembleRetriever` для RRF; обязательство относится к алгоритму, а выбор библиотек уточнён в §11. Слияние учитывает позиции, а не складывает несопоставимые raw scores двух поисковиков.

Оба индекса используют один актуальный набор чанков. Источник, позиция и версия сохраняются. После рестарта BM25 восстанавливается из сохранённого корпуса. Параметры chunking, overlap и глубины поиска выносятся в конфиг и выбираются по проверке §32, а не объявляются оптимальными заранее.

Разбиение учитывает законченные медицинские высказывания: название анализа + значение + единица, препарат + доза, рекомендация + срок, утверждение + отрицание. Для превышающего лимит блока допускается разбиение с сохранением достаточного контекста; это проверяется примерами у границ чанка. Сложная медицинская онтология не вводится.

# 14. Медицинские форматы документов

По уточнению форматов в `[КОНС]` обязательный набор медицинского проекта:

```text
.pdf  — только PDF с извлекаемым текстовым слоем, без OCR
.txt  — текстовые записи и транскрипты
.md   — Markdown, обрабатываемый как недоверенный текст
```

Этот набор применяется к разрешённому MCP-корпусу и входному медицинскому содержимому архива. В кабинете достаточно существующей загрузки PDF и вставки текста TXT/MD в форму заметки/транскрипта; отдельный новый файловый импорт TXT/MD не требуется этой редакцией. Уже имеющиеся безопасные loaders допустимо оставить как совместимость, но такие файлы не нужны для минимального корпуса и не служат доказательством медицинских сценариев. Кодовые файлы никогда не выполняются. Заявленный объём §23 считается по поддерживаемым медицинским документам, а не по искусственному наполнению кодом или эталонам ответов.

<a id="section-15"></a>

# 15. Corrective RAG и проверка выдачи

Обязательное алгоритмическое ядро сохраняется из `[RAG]`; выходная privacy-проверка принята проектом по `[КОНС]`:

```text
User Query → Rewrite Query → Retrieve BM25 + vector → RRF
                                               ↓
                                     Grade each chunk yes/no
                                      ↙                 ↘
                       достаточно контекста       недостаточно контекста
                              ↓                         ↓
                    Generate answer + sources     Broaden Query
                              ↓                   Retrieve снова
                локальный ответ кабинету          максимум 2 повтора
                              ↓
         для MCP: общий privacy pass ответа и всех источников
                              ↓
         очищенная выдача / ограниченный ответ / безопасный отказ
```

## 15.1 Узлы и граница

`rewrite_query` сохраняет даты, числа, отрицания и ключевые сущности. `retrieve` использует оба индекса, RRF объединяет ранги. `grade_chunks` оценивает каждый чанк локальной LLM; similarity threshold не заменяет этот шаг. `broaden_query` меняет поисковую формулировку. `generate_answer` использует найденный релевантный контекст и проверяемые ссылки; допустим проверяемый экстрактивный ответ при ограничениях маленькой модели.

Ни один узел не обращается к внешнему AI API. Текст источника — данные, а не команда раскрыть идентификаторы или изменить политику. Для публичного MCP privacy является обязательной последующей стадией; для `find_relevant_docs` она применяется непосредственно к найденным фрагментам. Ручная консультация использует тот же механизм, но сохраняет preview/review hash.

## 15.2 Лимиты и отказ

`retry_count` начинается с нуля: первоначальный retrieval плюс максимум два corrective-повтора, то есть не более трёх retrieval-проходов. Технические HTTP/LLM-повторы имеют отдельные ограниченные бюджеты. Порог достаточности задаётся конфигурацией и проверяется на корпусе.

При недостатке данных возвращается ограниченный ответ или сообщение о недостаточности контекста; общие знания или внешняя LLM не подменяют архив. Если privacy-проверка недоступна, невалидна, исчерпала время или не может безопасно сохранить смысл, MCP возвращает фиксированную безопасную ошибку/отказ без исходного результата, цитат и диагностических деталей. Прямой запрос идентификатора не разрешает его раскрытие.

## 15.3 Проверяемость

На синтетике локально доступны исходные/переформулированные запросы, ID чанков, grading, переходы, число повторов и соответствие источников. Это технические наблюдения, не скрытые рассуждения модели. Такие трассы не входят в MCP-ответ: они могут содержать текст запроса, пути и идентификаторы. На личных данных содержательные debug-логи выключены по умолчанию.

Ссылки проверяются сервером. Для MCP `responseRef` и обозначения `S1`, `S2` сопоставляются с настоящими источниками только локально; внешний хост не получает это соответствие. Проверки приватности и полезности выполняются после очистки, а не только на внутреннем ответе.

<a id="section-16"></a>

# 16. MCP-сервер и очищенный контракт

Настоящий MCP обязателен для проверки. По `[КОНС]` собственный вариант может менять список операций. Проект сохраняет четыре знакомых имени ради небольшого объёма и совместимости; их точный состав — наш выбор, а не неизменное ограничение курса. Дополнительные медицинские/диагностические tools не вводятся.

## 16.1 `index_folder`

Вход сохраняет форму:

```json
{"path": "./sample_docs", "glob": "**/*"}
```

Сканирует только разрешённый синтетический корень, извлекает текст, создаёт чанки/эмбеддинги и согласованно обновляет vector/BM25. Нормализованный путь, traversal и symlink проверяются; чтение личного архива или произвольного каталога недоступно. Повторная индексация не создаёт дубли.

Возвращает только безопасную агрегированную статистику: количество файлов/чанков, пропусков/ошибок и состояние операции. В выходе нет списка имён, путей, исходных исключений, содержимого или отражения входного `path`/`glob`. Генеративная LLM и извлечение медицинских фактов не вызываются; fixed-schema счётчики не требуют LLM-очистки. Подробности ошибок доступны только локально.

## 16.2 `ask_question`

Вход — предметный вопрос, например:

```json
{"question": "Какой интервал до повторного визита записан в синтетической истории?"}
```

Вызывает полный Corrective RAG, затем общую проверку правилами и локальной LLM для ответа и всех цитируемых фрагментов. Пример разрешённой формы (иллюстрация, не утверждение о существующем fixture):

```json
{
  "responseRef": "opaque-fresh-response-reference",
  "answer": "В синтетической записи повторный визит рекомендован через 17 дней. [S1]",
  "sources": [{"reference": "S1", "text": "Повторный визит рекомендован через 17 дней."}]
}
```

Состав дополнительных полей фиксируется безопасной схемой; в ней допустимы безопасный код отказа и флаг недостатка контекста. Нельзя сериализовать внутренний объект RAG целиком. Внешний результат не содержит исходных названий/имён файлов/путей, `documentId`, `chunkId`, версии исходного файла, необработанных metadata, таблицы замен, исходного вопроса или `trace`.

`responseRef` создаётся заново для результата и не вычисляется из медицинских данных или пути. `S1` действует только внутри этого результата и не является стабильным ID пациента/документа. Соответствие `responseRef + S1` реальному найденному источнику хранится только локально; в публичном MCP нет tool разрешения этой ссылки в исходник. Полные источники доступны пользователю в локальном кабинете.

## 16.3 `find_relevant_docs`

Вход — `query` и ограниченный `top_k`:

```json
{"query": "план повторного визита", "top_k": 5}
```

Выполняет BM25 + vector → RRF и возвращает ранжированные **очищенные** фрагменты с `responseRef` и непрозрачными `S1`, `S2`. Не выполняет генерацию предметного ответа, LLM-rewrite или LLM-grading. При этом **локальная LLM вызывается для privacy-проверки фрагментов**: это явное изменение прежнего контракта, разрешённое адаптацией проекта. Требование «без генерации ответа» не означает «без проверки приватности».

Правила очистки, безопасной схемы и отказа те же, что у `ask_question`. Нельзя получить исходную цитату в обход privacy через второй инструмент, метаданные или ошибку.

## 16.4 `index_status`

Аргументов нет. Только безопасные агрегаты: состояние EMPTY/READY, фиксированный корпус mcp_demo, число файлов/чанков и параметры chunking. Время индексирования намеренно не публикуется: оно не нужно для предметной задачи. Нет содержимого и списка источников. Пример для defaults до первого индексирования:

```json
{"status": "EMPTY", "corpus": "mcp_demo", "files": 0, "chunks": 0, "chunkSize": 900, "chunkOverlap": 120}
```

Модели, включая embedding, не вызываются. Пустой статус воспроизводится безопасным сбросом только demo-индекса.

## 16.5 Descriptions и самостоятельный выбор

Описание сервера объясняет предмет: поиск по синтетическим медицинским документам о визитах, анализах, назначениях и рекомендациях; ответы основаны на локальных источниках, проходят очистку и не являются медицинским советом. Указано, что нет доступа к личному архиву. Инструменты различают индексацию, агрегированный статус, готовый ответ и поиск очищенных фрагментов.

На проверке host-агент получает предметный вопрос без указания «используй MCP» и должен выбрать подходящий tool по descriptions. Записываются фактический вызов, конфигурация host и результат. Проверка Inspector не заменяет этот сценарий; один успешный host не гарантирует работу всех моделей.

## 16.6 Транспорт и ошибки

Используется локальный Streamable HTTP endpoint. В репозитории предоставлены готовый VSCode Copilot config, адрес/порт и инструкция; отдельно проверяется MCP Inspector. Endpoint работает только с `mcp_demo`; параметра переключения корпуса нет.

Ошибки любых tools, валидации и транспорта не отражают пользовательский запрос, `path`, содержимое или stack trace. Разрешены фиксированные безопасные сообщения и технические коды. Если privacy или требуемая для содержательной выдачи модель недоступны, ask/find не имеют резервной выдачи неочищенных данных; агрегированный status не требует модели. Эти fail-closed проверки распространяются и на прямую просьбу раскрыть вымышленное ФИО/номер карты, и на инструкции внутри документа.

# 18. External Consultation

## 18.1 Цель

Подготовить минимальный релевантный деперсонализированный медицинский контекст для ручной передачи внешней LLM.

## 18.2 Pipeline

```text
Question
   ↓
Relevant context selection
   ↓
Context minimization
   ↓
Rule-based de-identification
   ↓
Local LLM privacy pass
   ↓
Privacy warnings
   ↓
Preview
   ↓
Copy / Export Markdown
```

Один общий компонент правил и локальной LLM используется также на выходе MCP. У него общие категории удаления, проверка сохранности медицинского смысла и fail-closed. Внешний MCP-ответ и ручной экспорт — разные способы передачи: MCP автоматически отвечает подключённому хосту по синтетике, а личный пакет покидает кабинет только по решению пользователя через Copy/Markdown. Ручной review дополняет автоматическую проверку и не является единственным механизмом защиты.

## 18.3 Удаляемые / заменяемые категории

Минимально:

- patient name;
- exact date of birth;
- phone;
- email;
- address;
- patient identifiers;
- insurance identifiers;
- doctor names;
- clinic names;
- document identifiers.

При необходимости:

- exact dates;
- geographical information.

## 18.4 Псевдонимизация

Примеры:

```text
John Smith → [PATIENT]
Dr. Smith → [DOCTOR_1]
Hospital X → [HOSPITAL_1]
47 years → age range 40–50
2025-03-12 → T-14 months
```

## 18.5 Privacy warnings

Система должна отдельно предупреждать о потенциальных quasi-identifiers.

Пример:

```text
Rare diagnosis retained
Exact age retained
Unusual surgical procedure retained
Small geographical region retained
```

## 18.6 Ограничения

MVP не заявляет математическую или юридическую гарантию полной анонимизации.

Пакет личной консультации считается деперсонализированным и минимизированным текстом, требующим ручной проверки. Для MCP действует отдельная автоматическая граница выдачи синтетического корпуса (§16): наличие проверки не превращается в гарантию полной анонимности.

## 18.7 Точность и граница экспорта

Очищается не только выбранный контекст, но и вопрос пользователя, заголовки и окончательно сгенерированный текст. Не экспортируются имена исходных файлов, PDF metadata, локальные пути, внутренние UUID/source refs и таблица замен. Выдаётся новый текст, а не изменённый оригинальный PDF.

В MVP достаточно одного сценария подготовки по вопросу, без конструктора сложных политик. Псевдонимы устойчивы внутри одного пакета. Даты можно представить как `T0` и интервалы; расчёт выполняется по сохранённым данным, а не приблизительно моделью. При неизвестной дате точный интервал не выдумывается. Числа, единицы, дозы, отрицания и порядок событий не меняются молча.

Экспортируемый текст должен совпадать с просмотренным и подтверждённым. После правки подтверждение сбрасывается. Неудачная проверка приватности означает безопасную ошибку и блокировку выдачи подготовленного пакета; исходник не предлагается как запасной экспорт. Успешно подготовленный пакет требует просмотра и подтверждения точного content hash, любая правка сбрасывает его. Редкие клинически важные сведения помечаются предупреждением; решение об их сохранении остаётся у пользователя.

<a id="section-23"></a>

# 23. Seed / demo data

## 23.1 Происхождение и готовность

Основной набор — синтетическая история вымышленного пациента. Медицинские fixtures, включая отрицательные privacy-примеры, полностью вымышлены. Реальные документы и открытые записи реальных людей не используются. Наличие файла в Интернете не является разрешением включать его в Git.

В репозиторий входят готовые demo-данные; генератор при необходимости прилагается дополнительно. Преподавателю не нужно обращаться к внешней LLM, вручную вводить записи или искать датасет после запуска.

Синтетические документы явно маркируются. Их числа не выдаются за действительные медицинские рекомендации. Реальные документы пользователя, индексы и дампы в репозиторий не входят.

## 23.2 Прикладной seed собственного варианта

Принятый для проекта объём:

- не менее 30 медицинских записей суммарно; представлены PDF с текстовым слоем, транскрипты и заметки;
- история минимум за два календарных года и несколько типов документов;
- не менее 15 тегов;
- история исправлений минимум для 5 документов или фактов;
- связанные факты и события для timeline, фильтров и dashboard;
- реальные файлы синтетических оригиналов и корректные ссылки provenance для seed-фактов.

Числа 30, 15, 5 и два года — наши критерии собственного варианта, а не обязательные нормы всех full-stack заданий. Папки и wiki-связи из варианта 5 не добавляются.

Заранее подготовленные извлечения допустимы для быстрого наполнения demo, но маркируются как seed. Они не изображают только что выполненный inference. Новая загрузка и новый вопрос должны реально проходить локальный pipeline.

## 23.3 Корпус `sample_docs`

По `[RAG]` и `[КОНС]` сохраняется не менее 500 КБ документов. Медицинский набор содержит PDF с текстовым слоем, TXT и MD; семь исходных форматов больше не являются условием сдачи.

Проект сохраняет нижнюю границу `500 × 1024 = 512000` байт полезного индексируемого содержимого. Manifest фиксирует размеры и SHA256 файлов, а порог подтверждается отдельно по текстовым TXT/MD без бинарного размера PDF. Текущий набор v1.2 содержит 42 файла и 663711 файловых байт; один только TXT/MD-текст — 661410 байт, что уже превышает порог. PDF-поддержка проверяется отдельно. Веса, бинарный overhead, изображения без текста, эталонные ответы, служебный мусор и искусственные дубли не учитываются как полезный корпус.

Помимо записей корпус содержит короткое описание структуры и терминов. Вымышленные имена, телефоны, email, номера карты/документа присутствуют в отдельных отрицательных privacy-fixtures, включая имена файлов и цитаты, чтобы тестировать настоящую очистку. Они явно обозначаются как искусственные и не выдаются за реальные контакты. Эталоны и запрещённые к выдаче идентификаторы хранятся в оценочном наборе вне индекса.

## 23.4 Проверочные факты

README содержит вопросы, ожидаемые необычные факты и точные исходные файлы. Факты находятся в самих документах, а не только в README и ожидаемом ответе теста. Эталонный файл ответов исключается из индексируемого корпуса.

Пример формы: «В синтетической записи повторный визит рекомендован через 17 дней». Это иллюстрация, а конкретные существующие факты и исходники перечисляются в README. Номер карты, код пациента или документа не выбираются положительным проверочным фактом: корректная privacy-проверка должна удалить такой идентификатор.

Для проекта принимается не менее 10 фактов разрешённого содержания: значение анализа с единицей, срок повторного визита, доза, длительность, отрицание или неизвестность приёма. Их количество — наша проверочная граница. Ответ описывает, что записано в синтетическом документе, а не подтверждает медицинскую правильность. На реальной локальной модели проверяются одновременно сохранение факта после очистки и отсутствие вымышленных идентификаторов; локальное сопоставление непрозрачной ссылки подтверждает нужный источник.

# 24. Прикладной seed и демонстрационный MCP-индекс

Full-stack после запуска должен содержать seed. При этом `[RAG, «Процесс сдачи»]` начинает проверку с пустого `index_status()`. Эти условия выполняются одновременно через два пространства данных одного поискового движка.

| Пространство | Назначение | Инициализация | Доступ |
|---|---|---|---|
| `archive` | Кабинет и Ask Archive | Seed автоматически; прикладной индекс готовится автоматически с видимым статусом | Внутренний API приложения |
| `mcp_demo` | Проверка четырёх MCP-инструментов | Пустое при первом чистом запуске | Опубликованный локальный MCP |

Сценарий на чистом demo-хранилище:

```text
index_status()                    → status=EMPTY, files=0, chunks=0
index_folder("./sample_docs")     → индексирование синтетического корпуса
index_status()                    → status=READY, files/chunks, параметры chunking
ask_question("...")               → очищенный ответ + responseRef + S1
find_relevant_docs("...", top_k=5) → очищенные ранжированные фрагменты
```

Обычный повторный запуск не обнуляет индекс. Для повторения проверки README описывает безопасный сброс только `mcp_demo`, а не удаление личных документов или всех Docker volumes пользователя.

Коллекции сами по себе не являются полной security-изоляцией. MCP-handler получает только разрешённый корпус, не принимает `corpus_id` от хоста и не умеет читать произвольные пути архива. Один код RAG используется обоими интерфейсами без двух независимых реализаций.

<a id="section-25"></a>

# 25. Приватность и безопасность

## 25.1 Защищаемая граница

Оригиналы, текст, факты, история, эмбеддинги и пакеты консультации остаются локальными чувствительными данными. Цель MVP — исключить автоматическую отправку личного архива, контролировать выход синтетических данных через MCP и не допустить обходы ручного экспорта; защита от скомпрометированного хоста и полная анонимность не заявляются.

Внешних LLM API/SDK, шлюза к внешнему LLM-провайдеру, его ключей, web search и произвольного shell в приложении нет. Существующий локальный nginx ingress и фиксированный proxy к host Ollama решают сетевую задачу; они не являются исключённым внешним AI-gateway. Текст документов не должен попадать во внешнюю телеметрию и error-reporting.

## 25.2 Сеть и входные данные

UI без авторизации, Swagger и демонстрационный MCP публикуются по умолчанию только на loopback. БД и внутренний AI API не публикуются без необходимости. Это однопользовательское приложение для доверенного локального устройства, не публичный веб-сервис.

Рабочим сервисам ограничивается исходящий Интернет-доступ; для host Ollama разрешается явно заданное локальное соединение. Проверяется фактическая связность, а не только строка `internal: true` в Docker YAML. После подготовки UI, шрифты, PDF viewer и Swagger не должны требовать сторонних CDN.

Проверяются тип/размер загрузки, безопасное имя и серверный путь хранения. SQL-параметры валидируются и передаются через ORM. Markdown отображается без исполнения произвольного HTML/скриптов. PDF и текст считаются недоверенными данными: содержимое не получает права на новые tools, сетевую отправку или изменение конфигурации сервиса.

История хранится локально; содержательные тексты, таблицы замен и документы не печатаются целиком в обычные технические логи. Подробные диагностические traces допустимы на синтетике.

## 25.3 Две границы передачи

Личный архив: локальный контекст → правила + локальная LLM → точный preview → подтверждение content hash → ручной Copy/Markdown → дальнейшее решение пользователя. Приложение не вызывает внешнего провайдера.

MCP: запрос подключённого host-агента → только синтетический `mcp_demo` → общий RAG/retrieval → правила + локальная LLM → очищенная выдача хосту. Эта выдача является передачей данных, даже если в сервере нет внешних API-ключей. Она не требует ручного Copy и не открывает доступ к личному архиву.

Проверяются весь текст ответа, цитаты и любой выходной текст. Исходные названия, пути, `documentId`, `chunkId`, произвольные metadata и trace не входят в публичную схему. Вместо них выдаются непрозрачные `responseRef`/`S1`; соответствие доступно только локально. `index_folder`/`index_status` возвращают фиксированные безопасные агрегаты. Ошибки не отражают недоверенный ввод и исходные исключения.

Проверка правилами и локальной LLM обязательна для исходящего содержимого `ask_question` и `find_relevant_docs`. Прямой запрос имени/карты, просьба отключить очистку, инструкции внутри источника или недоступность проверяющей модели не разрешают сырую выдачу. При отказе проверки возвращается безопасное фиксированное сообщение без исходного текста. Очистка не должна молча менять медицинские числа/единицы/дозы/отрицания; если безопасный ответ не получается, требуется отказ.

Локальная модель внутри MCP не делает локальным дальнейшее использование ответа хостом. Path traversal, symlink и смена корпуса запрещены. Это граница штатных API, не защита от произвольного выполнения кода внутри AI-сервиса. Privacy-тесты на синтетике показывают конкретное поведение, не доказывают полную анонимность.

## 25.4 Разработка и публикация

AI для разработки кода отделяется от AI работающего архива. В контекст coding-агентов, GitHub, CI, issue, screenshots и REPORT передаются только код, синтетические примеры и безопасные технические данные. Реальные медицинские документы, дампы и индексы исключаются из репозитория.

Для личного использования используются отдельные каталоги/volumes без demo seed. Это разделение сред, не multi-user. Публикация проверяется на секреты и настоящие персональные данные.

## 25.5 Подготовка и хранение

Первичная установка может загружать образы, библиотеки и веса. Этот этап не обрабатывает медицинские документы; downloader/init-компоненты не получают к ним доступ. После подготовки модели и приложение должны работать без внешних AI-сервисов и новых автоматических загрузок.

Шифрование диска ОС рекомендуется для личного применения. Собственное управление ключами, безопасные резервные копии и доказанное стирание копий остаются вне MVP. Нельзя заявлять, что Docker volume уже зашифрован либо soft delete гарантирует уничтожение данных.

# 26. Error handling

Минимальные error cases:

- unsupported file type;
- scanned PDF without text layer;
- malformed PDF;
- parser failure;
- LLM unavailable;
- embedding model unavailable;

# 28. Локальная LLM и конфигурация

## 28.1 Требования источников

`[RAG]` предусматривает небольшую локальную модель через Ollama. Указанные Phi-3-mini и Qwen2.5-3B — примеры, не единственные допустимые модели.

Лекция разрешает использовать Ollama на локальном хосте преподавателя вместо обязательного запуска внутри Docker; нужны точные модели и инструкция подготовки `[ЛК-05]`. Внешние AI API в работающем RAG не используются. Послабления третьей CAD-темы к этому проекту не относятся.

## 28.2 Проектный runtime

Сохраняется Ollama. Точная маленькая модель для сдачи выбирается после проверки extraction, grading и генерации на синтетике. Предпочитаемый пользователем более мощный локальный Qwen 3.8 остаётся настраиваемым вариантом; его наличие, тег и параметры не объявляются проверенными данным документом.

```text
LLM_PROVIDER=ollama
LLM_BASE_URL=<разрешённый локальный endpoint>
LLM_MODEL=<закреплённый после проверки тег>
EMBEDDING_PROVIDER=chroma_default или ollama
EMBEDDING_MODEL=<выбранная embedding-модель>
RAG_MAX_CORRECTIVE_RETRIES=2
```

Плейсхолдеры допустимы в спецификации, но перед сдачей стандартная конфигурация должна содержать конкретные работающие значения. Модель, endpoint, параметры поиска и лимиты не зашиваются в код.

## 28.3 Эмбеддинги

Базовое задание допускает встроенную модель ChromaDB. Переключаемая через конфиг embedding-модель Ollama — необязательное дополнительное задание. Для MVP достаточно одного проверенного локального provider; нельзя помечать переключение реализованным без теста.

Версия embedding-модели связана с версией индекса. При несовместимой смене требуется пересоздание, а не смешивание векторов. Веса подготавливаются до offline-работы; первый embedding-запрос не должен неожиданно требовать Интернет при обработке личного архива.

## 28.4 Фиксация после испытаний

В README и результатах evaluation фиксируются модель и digest/версия при доступности, параметры генерации, контекст, embedding-модель, версии зависимостей, ОС и CPU/RAM/GPU проверенной среды, фактическое время операций. Заранее не обещается скорость на любом компьютере или GPU-ускорение в любом контейнере.

# 29. Docker Compose и два режима Ollama

## 29.1 Стандартный all-in-one режим

Сохраняется команда письменных заданий:

```bash
git clone <repo>
cd <repo>
docker compose up
```

Компоненты: frontend, NestJS backend, PostgreSQL, Python AI/RAG-service и Ollama. ChromaDB in-process. Если требуется, модели автоматически подготавливает init/provisioning service; стандартный путь не требует ручного `ollama pull` и редактирования обязательных конфигов.

Миграции и идемпотентный demo seed выполняются автоматически. Прикладной индекс подготавливается с видимым статусом; `mcp_demo` остаётся пустым. Повторный запуск не перезаписывает пользовательские изменения и не дублирует seed.

На хост не требуется отдельно устанавливать Python, Node.js, Go или БД. GPU не является безусловным условием старта: для небольшой модели предусмотрен CPU-путь с честно указанными ограничениями.

## 29.2 Разрешённый лекцией host-Ollama режим

Приложение, БД и MCP работают в Compose; модель — в локальном Ollama преподавателя `[ЛК-05]`. README содержит отдельную точную команду/override и сведения о подготовке:

- модели и команды загрузки;
- адрес, по которому контейнер реально достигает хоста;
- проверка соединения, доступности модели и короткого запроса;
- особенности испытанных Windows/Docker/WSL или Linux-сред;
- отключение лишнего контейнера Ollama в этом режиме.

Не предполагается, что контейнерный `localhost` автоматически означает хост. Точная схема подключения проверяется, а не оставляется преподавателю для угадывания.

Это явно разрешённое лекцией исключение. Оно не заменяет упаковку остальных runtime-зависимостей в Docker и не требует другого локального inference-продукта.

## 29.3 Подготовка и готовность

Чистая установка может требовать Интернет для образов и весов. Это оговаривается отдельно от локальной работы с медицинскими данными. Никакие реальные документы не доступны компонентам скачивания.

README содержит реальные адреса UI/Swagger/MCP, состояния готовности и диагностические действия. `ready` не показывается, пока обязательный для операции компонент недоступен. После подготовки проверяется отсутствие внешних обращений при штатной работе; для host Ollama разрешено только локальное соединение.

# 32. Тестирование и проверка качества

## 32.1 Full-stack

`[FS]` требует не менее 10 unit/integration тестов. Наш отдельный набор покрывает создание заметки, upload, отклонение неверного файла, пагинацию, поиск/фильтры, изменение документа, soft delete, restore, исправление факта/историю, timeline и dashboard. Число тестов может быть больше минимального.

Проверяются обе стороны валидации и критические связи: удалённое не возвращается в поиске, исправление сохраняется при reprocess, оригинал выдаётся только через контролируемый маршрут.

## 32.2 RAG/MCP

`[RAG]` требует минимум 10 тестов, включая mock LLM unit-тесты графа, тесты индексатора и e2e MCP-инструментов. В проекте это отдельная группа минимум из 10. Суммарные 20 — наше правило прозрачного покрытия двух заданий, а не дословный единый минимум курса.

Покрываются медицинские PDF/TXT/MD, внутренние metadata чанков, повторное индексирование, BM25/vector/RRF, rewrite, grading, достаточный/недостаточный контекст, broaden, лимит повторов и четыре выбранных MCP-инструмента. Внешние ответы проверяются по очищенной схеме: непрозрачные источники, локальное сопоставление, отсутствие raw metadata/trace и безопасные ошибки.

E2e MCP проходит через настоящий транспорт/клиент против сервера, а не только прямой вызов Python-функции. В детерминированных CI-проверках LLM/embeddings могут быть тестовыми адаптерами с явной маркировкой.

## 32.3 Настоящая маленькая модель

Mock-тесты не доказывают качество RAG. Перед сдачей выполняется отдельный прогон реального Ollama и настоящей embedding-модели. Лекция предусматривает перефразированные, простые и неожиданные вопросы, а также итерации над чанками `[ЛК-07]`.

Принимаемый проектом минимум — 20 оценочных вопросов, в том числе не менее 10 проверочных фактов. Это собственные численные критерии.

| Класс | Проверка |
|---|---|
| Точный факт | Разрешённое медицинское число с единицей, срок, доза или деталь рекомендации; не идентификатор документа/пациента |
| Перефразирование | Тот же смысл без дословного совпадения терминов |
| Обзорный вопрос | Что хранится в этом корпусе, как понимать его структуру |
| Несколько документов | Последовательность событий и рекомендаций |
| Даты/отрицания | Не потеряны условия, отрицания и даты событий |
| Отсутствие ответа | Система признаёт, что нужных данных нет |
| Противоречие | Различие источников показано, а не скрыто |
| Посторонний вопрос | Не создаётся выдуманный ответ от имени архива |

Каждый случай задаёт исходные документы, ожидаемые факты/допустимый отказ и ожидаемые ссылки. Эталоны хранятся вне индексируемого корпуса. Оценивается смысл и факты, не полное посимвольное совпадение.

Фиксируются наличие нужного источника в top-k, правильность фактов и ссылок, отказ при отсутствии данных, число corrective-повторов и фактическое время. Неудачи сохраняются, а не удаляются ради хороших цифр.

Все заявленные проверочные факты должны быть найдены и сохранены после privacy с правильными источниками в финальном контрольном прогоне. Для MCP источники проверяются по локальному соответствию `responseRef + S1`, не по раскрытию исходного пути. Для остальных классов документируются результат и ограничения. Универсальный процент точности на любых медицинских вопросах не обещается.

Сравниваются как минимум две разумные конфигурации chunking/overlap; фиксируется, почему выбрана финальная. Помимо размера проверяются пограничные случаи: анализ/значение/единица, препарат/доза, рекомендация/срок и утверждение/отрицание остаются совместно доступными в контексте. Это наши предметные критерии качества по рекомендации консультации; сложная онтология и новый UI не требуются.

## 32.4 Host-агент

После подключения по готовому конфигу задаётся предметный вопрос без фразы «используй MCP». Фиксируются фактический выбор инструмента, вызов и ответ. Проверка только через Inspector этот сценарий не заменяет. Скрытые рассуждения модели не требуются.

## 32.5 Приватность и полезность на синтетике

Один набор вымышленных идентификаторов проверяет общий privacy-компонент, ручную консультацию и оба MCP-инструмента выдачи. Тестируется вся сериализованная выдача, включая ошибки и metadata, а не только `answer`.

| Сценарий | Ожидаемый результат |
|---|---|
| Предметный вопрос рядом с ФИО/контактом/номером карты | Полезный факт и непрозрачная ссылка сохранены, идентификаторы отсутствуют |
| Прямой запрос ФИО, телефона, номера карты | Идентификатор не выдаётся; допустим безопасный отказ |
| `find_relevant_docs` по тому же документу | Очистка не обходится выдачей исходного фрагмента |
| Идентификатор в имени файла, заголовке, цитате, metadata | Нет утечки через текст/пути/ID/trace; наружу только разрешённая схема |
| Неверный path/glob/аргумент, parser/provider exception | Фиксированная безопасная ошибка, без отражения входа и внутреннего пути |
| Проверяющая модель недоступна, timeout или невалидный результат | Fail-closed: исходный текст не выдаётся |
| Инструкция внутри документа раскрыть данные | Источник остаётся данными и не меняет политику |
| Медицинские числа, единицы, дозы, сроки, отрицания | Смысл не меняется после очистки; сравниваются с источником |
| Повторная выдача источника | Свежий непрозрачный responseRef; сопоставление с реальным источником остаётся локально |
| Ручной экспорт после изменения preview | Старый review hash недействителен; экспорт только точного подтверждённого текста |
| Попытка выбрать личный корпус или выйти через symlink | Публичный MCP отказывает без раскрытия данных |

Детерминированные тесты со stub/mock LLM и настоящие локальные Ollama-проверки записываются отдельно. Форматные тесты без вызова модели не выдаются за доказательство качества очистки. Успешный набор означает прохождение перечисленных случаев, а не полную анонимность.

## 32.6 Результаты

Команды находятся в README, случаи и конфигурации — в `evaluation/`, реальные машинные результаты — в `docs/evaluation/`. В них нет настоящих медицинских данных. Авторский разбор выполненных экспериментов добавляется лично в REPORT; результаты и опыт не сочиняются заранее.

# 33. CI

GitHub Actions подключается с первых рабочих изменений. Pipeline: lint → тесты frontend/backend/Python/MCP → сборка приложения и Docker-образов/проверка Compose.

В корне находятся README.md, ARCHITECTURE.md, REPORT.md и PROJECT_SPECIFICATION.md; прилагается конфиг MCP для VSCode Copilot. Первые три документа и конфиг предусмотрены письменными заданиями. AGENTS.md, TASKS.md и evaluation-файлы — наш способ организации проекта.

Назначение и собственный вариант; стандартный `docker compose up`; отдельный host-Ollama режим с конкретными моделями; адреса UI/Swagger/MCP; готовый конфиг IDE; seed и demo-сценарий; вопросы/проверочные факты/точные источники; объём корпуса; команды тестов и evaluation; безопасный сброс demo-индекса; ограничения приватности и MVP.

## 34.3 ARCHITECTURE.md

Создаётся и коммитится до начала кодирования `[FS, «Критерии оценки»]`. Содержит сервисы, данные, RAG-граф, privacy boundaries и план. Значимые изменения решений фиксируются с причиной.

Нельзя подделывать даты и последовательность Git, чтобы изобразить архитектуру до кода. Эта спецификация — материал для подготовки проекта, не доказательство истории репозитория.

## 34.4 REPORT.md — личный текст автора

В лекции прямо сказано: основную часть REPORT студент пишет сам; AI-вставки явно обозначает `[ЛК-03]`. Отчёт ведётся по мере разработки, а не сочиняется целиком в конце.

Содержимое: выбранный workflow; фактически использованные модели/агенты/инструменты; организация контекста; реальные этапы, проблемы и решения; удачные/неудачные промпты; проверки и выводы; вопросы преподавателю. По письменным заданиям нужен минимум один показательный промпт с кратким разбором.

Рекомендуемый формат записи, не готовый личный отчёт:

```text
Дата / задача / commit
Что планировал сделать
Какой агент и модель реально использовались
Какой контекст и инструкции передал
Что получилось и что не получилось
Как проверил и что изменил
Ссылка на промпт/лог/результат
Открытый вопрос
```

AI может помочь шаблоном, извлечением фактических логов или помеченной редактурой, но не пишет от лица студента выдуманную историю работы. Вставка обозначается, например: «AI-фрагмент, модель/инструмент, дата, цель». Настоящих медицинских сведений в отчёте нет.

Эта спецификация подготовлена AI и не должна копироваться в REPORT как личный рассказ автора.

## 34.5 Статусы

Таблицы §37–38 определяют требования и необходимые доказательства, а не текущую оценку. Фактический статус публикуется в TASKS и docs/VALIDATION.md: путь к тесту, commit, команда и результат. Изменённый v1.2 контракт проверяется заново; старый зелёный результат не переносится на него автоматически.

<a id="section-36"></a>

# 36. MVP acceptance criteria

Это план приёмки, не свидетельство уже работающей реализации.

Проект считается готовым, если выполняется весь следующий сценарий.

## Application

1. `docker compose up` запускает приложение.
2. Browser UI доступен.
3. Seed data уже присутствует.
4. Archive показывает документы.
5. Работают pagination, search и filters.
6. Можно создать note.
7. Можно загрузить text-based PDF.
8. Документ обрабатывается локальной LLM.
9. Видны summary и structured facts.
10. Fact показывает provenance.
11. Fact можно исправить.
12. Исправление видно в history.
13. Timeline отображает события.
14. Dashboard содержит статистику и график.
15. Ask Archive возвращает ответ с sources.
16. External Consultation создаёт sanitized preview.
17. Результат можно скопировать / экспортировать.
18. Swagger UI доступен.

## MCP / RAG

1. MCP подключается к host.
2. `index_status()` возвращает пустой индекс.
3. `index_folder("./sample_docs")` индексирует corpus.
4. Поддерживаются PDF с текстовым слоем, TXT и MD; медицинский корпус содержит не менее 512000 байт полезного индексируемого текста.
5. `index_status()` показывает files/chunks.
6. `find_relevant_docs()` выполняет hybrid retrieval и privacy-проверку найденных фрагментов без генерации предметного ответа.
7. BM25 и vector results объединяются через RRF.
8. `ask_question()` запускает LangGraph.
9. Grade node оценивает chunks.
10. При недостатке контекста выполняется broaden + retry.
11. Retry ограничен двумя циклами.
12. Ответ и все источники проходят общий privacy pipeline; наружу выдаются responseRef/S1 без исходных путей, заголовков, ID и trace.
13. Host agent выбирает MCP tool по `description` без подсказки «используй MCP».
14. Прямой запрос идентификатора, ошибка проверки или недоступная LLM не приводят к сырой выдаче.
15. `index_folder` и `index_status` выдают только безопасные агрегаты; ошибки не отражают исходный ввод.

## Process / quality / privacy

1. Есть реальный evaluation на выбранной маленькой модели, не только mock-тесты.
2. Не менее 10 разрешённых медицинских проверочных фактов найдены с правильными источниками после очистки; идентификаторы отсутствуют. Остальные результаты и ограничения задокументированы.
3. REPORT написан автором по ходу работы, AI-вставки отмечены; ARCHITECTURE действительно предшествует коду.
4. Оба режима Ollama проверены по точным инструкциям.
5. Demo MCP не имеет API-пути к личному архиву и выдаёт только проверенную синтетику; личный экспорт содержит именно просмотренную/подтверждённую версию без автоматической отправки.
6. Изменение/удаление документа не оставляет скрытую устаревшую выдачу; reprocess сохраняет ручные поправки.
7. Статусы подтверждены командами, тестами и commit; изменение требований не объявляется уже пройденной приёмкой.
8. Пограничные chunking-тесты сохраняют пары анализ/значение/единица, препарат/доза, рекомендация/срок и отрицания.
9. Настоящая Ollama privacy-проверка и mock-тесты отмечены как разные доказательства.

# 41. Итоговая концепция

Система представляет собой локальный персональный медицинский архив, объединяющий обычное full-stack приложение и локальный AI knowledge layer.

Ключевая последовательность:

```text
Medical Document
        ↓
Local Storage
        ↓
Parsing
        ↓
Local LLM Extraction
        ↓
Structured Facts + Provenance
        ↓
Archive / Timeline / Search
        ↓
Corrective RAG
        ↓
Local Answer with Sources
```

Для внешнего MCP-хоста: синтетический корпус → общий RAG/retrieval → правила и локальная LLM privacy → очищенный ответ/фрагменты + непрозрачные источники либо безопасный отказ. Передача такого ответа отличается от ручного экспорта личного архива.

Для внешней консультации:

```text
User Question
        ↓
Local Context Selection
        ↓
De-identification
        ↓
Manual Privacy Review
        ↓
Copy / Markdown Export
        ↓
User manually submits elsewhere
```

Главные свойства проекта:

- local-first;
- privacy-oriented;
- explainable through provenance;
- human-correctable;
- structured;
- RAG-enabled;
- reproducible;
- suitable both as a course project and as the foundation of a real personal medical archive.

# 42. Методология AI-разработки

## 42.1 Что подчёркивает лекция

Оцениваются организация работы с AI, контекст агентов, документация, продолжение свежей сессией, участие человека и проверка требований `[ЛК-02]`. Код предполагается генерировать AI в рамках выбранного процесса, а не просто предъявить результат одного промпта. Основной REPORT при этом пишет студент лично.

Следующий workflow — наш минимальный процесс, не дословно предписанная преподавателем методология. Конкретный coding harness выбирается при реализации; в отчёте называются фактически использованные инструменты.

## 42.2 Роли

Человек задаёт цель/ограничения, принимает архитектурные решения, проверяет diff и пользовательский результат, пишет личный журнал. Coding agent генерирует и исправляет код/тесты/техническую документацию. Проверять может тот же или отдельный агент, но окончательное принятие изменения остаётся за человеком.

Обычное исправление кода также поручается агенту. Фактические исключения не скрываются и при необходимости согласуются; нельзя заявлять полностью AI-сгенерированную работу, если процесс был другим.

## 42.3 Организация контекста

`PROJECT_SPECIFICATION.md` — что строим; `ARCHITECTURE.md` — устройство; `AGENTS.md` — правила и команды; `TASKS.md` — актуальная задача, проверка и следующий шаг. Значимые решения кратко фиксируются в `docs/decisions.md`.

Агент получает только относящиеся к задаче файлы и синтетические примеры. В инструкции закрепляются отдельные корпуса, выбранные четыре tools, медицинские PDF/TXT/MD, обязательное алгоритмическое ядро, общий privacy pipeline для всей MCP-выдачи, fail-closed и точный review hash личного экспорта. Язык/библиотеки и состав API не объявляются неизменными требованиями преподавателя. Проверки не подменяются выдуманными ответами. Личные медицинские документы не нужны для генерации кода.

## 42.4 Цикл задачи

1. Выбрать конкретное требование и критерий приёмки.
2. Передать агенту необходимые проектные документы, код и текущее состояние.
3. Получить небольшой план; проверить влияние на контракт, данные и приватность.
4. Сгенерировать реализацию и тесты.
5. Выполнить проверки, сохранить реальные ошибки и результат.
6. Провести ревью diff и сценария; исправить причину ошибки, а не только ожидаемый ответ теста.
7. Закоммитить осмысленное изменение, обновить состояние задач/решений.
8. Автор лично дополняет REPORT фактическим опытом работы.

Отдельный автоматизированный supervisor или orchestration framework не требуется. Достаточны ясные инструкции и небольшие проверяемые изменения.

## 42.5 Новая сессия агента

В конце сессии сохраняются текущая задача, принятые решения, изменённые файлы, выполненные команды и их результаты, известная ошибка и следующий шаг. Новый агент читает документы и handoff, затем сверяет их с Git и кодом.

Нельзя рассчитывать, что свежий агент помнит предыдущий чат. В handoff не включаются выдуманные выполненные действия и реальные медицинские данные. Контекст обновляется по факту изменений, а не накоплением бесконечной переписки.

## 42.6 Перед сдачей

Каждый пункт матриц §37–38 получает статус и доказательство. Независимый проход агентом полезен, но не заменяет человеческую проверку основных сценариев и clean-start.

В REPORT полезны настоящие примеры: неудачный chunking, потеря единиц, ошибка retries, неудачный tool description, восстановление контекста новой сессии. Такие истории включаются только если реально произошли.

# 43. Собственный вариант в формате преподавателя

### Собственный вариант: локальный медицинский архив с AI-каталогизацией, Corrective RAG и контролируемым деперсонализированным экспортом

Общие требования full-stack задания плюс:

**Функциональные:**

- Кабинет документов: PDF с текстовым слоем, текстовые файлы, заметки/транскрипты из формы; просмотр оригинала, изменение названия/даты/типа/тегов, мягкое удаление и восстановление.
- Полнотекстовый поиск, фильтры по датам/типам/тегам/статусам, пагинация, адаптивный интерфейс.
- Локальная AI-каталогизация: классификация, summary, умеренное извлечение диагнозов, симптомов, лекарств, анализов, процедур и рекомендаций без сложной онтологии.
- Provenance: документ, страница или текстовая позиция, цитата; проверка и ручное исправление фактов с сохранением исходного результата модели.
- Timeline событий с фильтрами и переходом к источнику; неизвестные даты явно обозначаются.
- Dashboard: количество/типы документов, обработка, распределение по времени и последние изменения.
- История: импорт, правка метаданных/заметки, AI-обработка, исправление факта, reprocess, удаление/восстановление.
- Ask Archive: локальный Corrective RAG с BM25 + vector/RRF, grading, ограниченными повторными поисками и ответами с источниками.
- Подготовка внешней консультации: локальный минимальный контекст, очистка идентификаторов правилами и LLM, точный preview, предупреждения, ручное подтверждение и Copy/Markdown. Внешних API и автоматической отправки нет.
- MCP: настоящий HTTP-сервер общего RAG с четырьмя выбранными инструментами; предметные descriptions и самостоятельный выбор host-агентом. Синтетический медицинский корпус PDF/TXT/MD, общая проверка правилами и локальной LLM, очищенные ответы/фрагменты с непрозрачными ссылками и безопасный отказ без сырых данных.

**Нефункциональные:**

- Один локальный пользователь без регистрации; UI без авторизации не предназначен для публичной сети.
- React/TypeScript + NestJS + PostgreSQL и Python AI/MCP; локальный Ollama; стандартный запуск Compose и отдельный документированный host-Ollama режим.
- Живой Swagger/OpenAPI, минимум 10 full-stack и 10 RAG/MCP тестов, CI lint/тесты/сборка, реальные проверки небольшой локальной модели.
- Новый публичный GitHub-репозиторий, ARCHITECTURE до кода, README, личный REPORT с методологией AI-разработки и маркировкой AI-вставок.
- Оригиналы не переписываются; реальные медицинские данные не включаются в demo/CI/репозиторий или контекст внешних кодинговых агентов.
- OCR, изображения, аудиотранскрипция, FHIR, multi-user и внешние LLM API вне MVP.

**Seed-данные:** не менее 30 синтетических записей с PDF, транскриптами и заметками; минимум два календарных года; 15 тегов; история правок минимум для 5 документов/фактов; связанные события и оригиналы. Отдельно — готовый RAG-корпус не менее 512000 байт медицинского текста PDF/TXT/MD, минимум 10 сохраняемых после очистки медицинских фактов в README и вымышленные идентификаторы для отрицательных privacy-проверок.

**Оценочный набор проекта:** минимум 20 разнообразных вопросов к реальному RAG, ожидаемые факты и локально проверяемые источники, сохранение медицинского смысла при chunking/очистке, прямые запросы идентификаторов и ошибки privacy. Фактические результаты и ограничения сохраняются отдельно от mock-тестов; host выбирает MCP-инструмент без подсказки.

После принятия фиксируется версия этого описания. Обязательства не меняются незаметно под уже написанный код.
