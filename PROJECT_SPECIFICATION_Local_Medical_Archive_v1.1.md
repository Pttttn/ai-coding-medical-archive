# 1. Цель проекта

Разработать локальное однопользовательское приложение для хранения, каталогизации, структурирования, поиска и анализа медицинских документов с использованием локальной большой языковой модели и Corrective RAG.

Система должна:

- хранить медицинские документы локально;
- поддерживать загрузку PDF с текстовым слоем, текстовых транскриптов приёмов и текстовых заметок;
- автоматически извлекать из документов структурированные медицинские факты;
- формировать медицинскую временную шкалу;
- обеспечивать обычный поиск и AI-поиск по архиву;
- сохранять provenance для AI-извлечённых фактов;
- позволять пользователю корректировать AI-извлечения с сохранением истории;
- готовить деперсонализированный текстовый пакет для ручной передачи внешней frontier LLM;
- не отправлять медицинские данные во внешние сервисы самостоятельно;
- предоставлять MCP-интерфейс с Corrective RAG для выполнения требований учебного задания.

Приложение проектируется как полноценный MVP будущего персонального медицинского архива, а не как демонстрация отдельных AI-функций.

# 2. Основные принципы

## 2.1 Local-first

Оригиналы, текст, факты, индексы и история остаются локально. Все модели, обрабатывающие архив, вызываются локально. В runtime нет внешнего LLM API, gateway и ключей frontier-провайдеров. Первичная загрузка образов/весов отделена от работы с медицинскими данными; установка без заранее доступных зависимостей не обещается полностью offline.

## 2.2 Human-in-the-loop

AI-извлечения — предложения модели. Пользователь проверяет источник и исправляет результат с историей. Неизвестное значение не выдумывается; предположение не становится установленным диагнозом, назначение не доказывает фактический приём лекарства, отрицание сохраняет смысл.

## 2.3 Provenance

У AI-факта должны быть документ и исходный фрагмент, при применимости — страница/позиция/chunk. Если подтверждение не найдено, результат не становится автоматически подтверждённым фактом: сохраняется как кандидат с предупреждением либо отклоняется. Ручные исправления маркируются отдельно от утверждений источника.

## 2.4 Структурированные данные и RAG

Timeline, фильтры и числовые представления используют структурированные данные. Свободный вопрос Ask Archive и MCP `ask_question` используют полный Corrective RAG. Универсальный агент, самостоятельно генерирующий SQL, не нужен для MVP.

Поправка пользователя не переписывает PDF. При ответе различаются исходный документ и пользовательская коррекция; исходная цитата не выдаётся за доказательство исправленного пользователем числа.

## 2.5 Контролируемый ручной экспорт

Система минимизирует и деперсонализирует контекст, показывает точный preview и предупреждения. Пользователь проверяет, копирует или сохраняет Markdown и самостоятельно отправляет его дальше. Никакой кнопки Send и автоматической отправки нет.

## 2.6 Воспроизводимость

Сохраняются версии модели, промпта, схемы и обработки. Намерения, реализация и выполненные проверки различаются. Нельзя заранее объявлять функцию реализованной, придумывать качество или восстанавливать несуществовавшую историю Git/REPORT.

- OCR сканированных PDF;
- изображения документов;

- DICOM;
- FHIR server;
- SNOMED CT normalization;
- ICD normalization;
- multi-user;
- функции чужих full-stack вариантов, не включённые в собственное описание §43;

- облачная синхронизация;
- мобильное приложение;

- автоматическое медицинское принятие решений;
- постановка диагноза как целевая функция продукта.

# 4. Пользователь

MVP рассчитан на одного локального пользователя.

Авторизация в первой версии не требуется.

Приложение должно запускаться в режиме zero-config с уже подготовленными demo/seed-данными для проверки.

Кабинет без авторизации предназначен для доверенного локального устройства и по умолчанию доступен только на loopback. Публичное размещение вне MVP. Demo и личное применение используют отдельные данные/volumes; это не функция нескольких пользователей.

# 5. Основные пользовательские сценарии

Числа и медицинские примеры ниже иллюстративны и относятся к синтетическим данным, а не к истории пользователя.

## UC-01. Загрузка PDF

1. Пользователь открывает Archive.
2. Нажимает Upload.
3. Выбирает PDF с текстовым слоем.
4. Backend сохраняет оригинальный файл.
5. Создаётся Document.
6. Из PDF извлекается текст.
7. Документ отправляется на локальную AI-обработку.
8. Создаются:
   - summary;
   - document type;
   - tags;
   - extracted facts;
   - chunks;
   - embeddings.
9. Документ становится доступен в Archive, Timeline и поиске.

## UC-02. Добавление транскрипта приёма

Пользователь создаёт текстовую запись типа `VISIT_TRANSCRIPT` и вставляет текст транскрипта.

Система обрабатывает его как медицинский документ:

- summary;
- specialty;
- diagnoses;
- symptoms;
- medications;
- recommendations;
- timeline event при известной дате; иначе событие остаётся без точной даты.

## UC-03. Создание личной заметки

Пользователь создаёт текстовую заметку, указывает:

- title;
- date;
- tags;
- content.

Заметка индексируется вместе с другими документами.

## UC-04. Просмотр документа

Страница документа отображает:

- название;
- тип;
- дату;
- статус обработки;
- tags;
- summary;
- исходный текст / ссылку на PDF;
- извлечённые факты;
- provenance;
- историю изменений.

## UC-05. Исправление AI-факта

Пример:

AI извлёк:

`LDL = 4.7 mmol/L`

Пользователь меняет значение на:

`LDL = 4.1 mmol/L`

Система:

- сохраняет исходное AI-значение;
- сохраняет новое значение;
- создаёт запись AuditEvent;
- показывает исправленное значение как актуальное.

## UC-06. Просмотр Timeline

Пользователь открывает Timeline и видит события в хронологическом порядке.

Пример:

```text
2025-03-12
Blood test
LDL 4.1 mmol/L

2025-03-27
Cardiology visit
Recommendation: ...

2025-04-01
Medication started
Atorvastatin 20 mg
```

Каждый элемент Timeline должен вести к источнику.

## UC-07. Обычный поиск

Пользователь вводит:

`тахикардия`

Система выполняет full-text search по индексируемому тексту.

Дополнительно доступны фильтры:

- date from / to;
- document type;
- tags;
- processing status.

## UC-08. Ask Archive

Пользователь спрашивает:

> Когда впервые упоминался повышенный LDL и какие рекомендации были даны?

Система запускает Corrective RAG:

1. rewrite;
2. hybrid retrieval;
3. grading;
4. при необходимости broaden + retry;
5. generation;
6. ответ + sources.

## UC-09. Подготовка внешней консультации

Пользователь вводит вопрос:

> Подготовь данные для внешней консультации о причинах роста ALT.

Система:

1. локально выбирает релевантный контекст;
2. минимизирует объём данных;
3. удаляет или заменяет очевидные персональные идентификаторы;
4. локальная LLM выполняет дополнительный privacy pass;
5. генерирует external consultation package;
6. показывает preview;
7. показывает privacy warnings;
8. после ручного подтверждения текущего текста позволяет Copy / Export Markdown.

Приложение не выполняет сетевую отправку.

# 6. UI / основные экраны

Поля:

- title;
- type;
- document date;
- created at;
- tags;
- processing status.

- pagination;
- search;
- filters;
- sort;
- open;
- edit metadata;
- delete;
- restore.

Режимы:

- upload PDF;
- create transcript;
- create note.

## 6.4 Document Details

Блоки:

1. metadata;
2. original document / extracted text;
3. summary;
4. extracted medical facts;
5. provenance;
6. tags;
7. history.

## 6.5 Timeline

Хронологический список событий.

Фильтры:

- event type;
- date range;
- document;
- category.

Содержит:

- поле вопроса;
- ответ;
- список sources;
- индикатор состояния;

## 6.7 External Consultation

Содержит:

- исходный вопрос;

- подтверждение проверки текущего текста;
- privacy warnings;
- Copy;
- Export Markdown.

## 6.8 History

Журнал:

- document uploaded;
- metadata updated;
- AI extraction completed;
- fact corrected;
- document reprocessed;
- deleted;
- restored.

## 7.11 ExtractionRun и ProcessingJob

Для каждой обработки сохраняются `document_id`, версия исходного текста, модель и digest при доступности, версии промпта/схемы/парсера, время, статус, исходный JSON и ошибки валидации. Это позволяет повторить обработку, не заменяя оригинал.

`ProcessingJob` хранит ID документа, операцию, статус, попытку и безопасный код ошибки. Достаточна простая очередь/worker на базе PostgreSQL; отдельный брокер в MVP не обязателен.

## 7.12 Уточнения целостности модели данных

Это инженерные условия уже выбранных фактов, истории и provenance, не новые требования лекции:

- Для редактируемого текста сохраняется версия/ревизия; provenance относится именно к использованной версии. Старый chunk не должен внезапно указывать на изменённую заметку.
- `event_date`/`document_date` могут быть неизвестны; дата загрузки хранится отдельно. Нет автоматической подстановки технической даты как медицинской.
- Статус утверждения источника (подтверждено в документе, предполагается, отрицается, назначено, неизвестно) отделяется от проверки пользователем (`UNREVIEWED`, `CONFIRMED`, `CORRECTED`, `REJECTED`).
- `confidence`, если его возвращает модель, не считается калиброванной вероятностью правильности. Проверка источника важнее самооценки.
- Сохраняются исходные единицы/формулировки; для лекарств — текст дозы/режима; сложная нормализация и автоматическое объединение состояний пациента вне MVP.
- У `ExternalConsultation` дополнительно сохраняются локальные source refs, версии генерации, статус `DRAFT/NEEDS_REVIEW/REVIEWED`, hash содержимого и hash просмотренной версии. Внешний Markdown не содержит внутренние refs/пути или таблицу замен.
- Схема логическая. Окончательные имена полей и миграции фиксируются в ARCHITECTURE и коде, не считаются уже созданными.

<a id="section-8"></a>

# 8. AI extraction schema

Локальная LLM должна возвращать структурированный JSON.

Пример:

```json
{
  "documentType": "LAB_REPORT",
  "documentDate": "2025-03-12",
  "specialty": null,
  "summary": "Routine blood test...",
  "tags": ["blood-test", "lipids"],
  "facts": [
    {
      "type": "LAB_RESULT",
      "name": "LDL",
      "valueNumber": 4.1,
      "valueText": null,
      "unit": "mmol/L",
      "eventDate": "2025-03-12",
      "confidence": 0.96,
      "provenance": {
        "page": 2,
        "sourceText": "LDL cholesterol 4.1 mmol/L"
      }
    }
  ]
}
```

Требования:

- JSON должен валидироваться;
- неизвестные значения не должны выдумываться;
- неподтверждённые поля должны быть `null`;
- источник должен сохраняться, если он доступен;
- AI extraction не модифицирует оригинальный документ.

Цитата проверяется на наличие в соответствующей версии источника. Валидный JSON сам по себе не подтверждает факт. При невалидном ответе допускается ограниченный технический повтор, затем понятная ошибка; этот лимит отделён от двух corrective-повторов RAG.

При повторной обработке сохраняется новый результат модели, но не затираются проверенные ручные исправления. Конфликт решается пользователем без сложного автоматического слияния. Показанное в JSON поле `confidence` иллюстрирует возможный ответ модели, не доказанную точность.

<a id="section-9"></a>

# 9. История и версионирование

История должна фиксировать минимум:

- загрузку документа;
- изменение metadata;
- завершение AI extraction;
- correction extracted fact;
- reprocessing;
- deletion;
- restoration.

Для исправляемых AI-фактов обязательно сохранять исходное AI-значение.

Оригинальный файл считается immutable.

Для изменяемых заметок/транскриптов сохраняется версия текста. Удалённые документы исключаются из обычного поиска, RAG, timeline и новых консультаций; восстановление возвращает их после актуализации индекса. BM25 и Chroma обновляются согласованно, повторная индексация не создаёт дубли.

Старые консультации — локальные снимки, не автоматически актуальный контекст после правки источника. В MVP soft delete не означает физическое стирание; срок 30 дней из варианта 5 не переносится. Для переиндексируемых записей либо исключается устаревшая версия, либо явно показывается её состояние.

<a id="section-13"></a>

# 13. RAG indexing

RAG corpus индексируется отдельно от PostgreSQL.

## Vector storage

ChromaDB in-process.

## Sparse retrieval

BM25 через `rank_bm25`.

## Hybrid retrieval

Используется:

```text
BM25 results
+
Vector results
        ↓
Reciprocal Rank Fusion
        ↓
Combined ranking
```

В реализации используется LangChain `EnsembleRetriever` для RRF согласно технологическому перечню задания. Слияние учитывает позиции, а не складывает несопоставимые raw scores двух поисковиков.

Оба индекса используют один актуальный набор чанков. Источник, позиция и версия сохраняются. После рестарта BM25 восстанавливается из сохранённого корпуса. Параметры chunking, overlap и глубины поиска выносятся в конфиг и выбираются по проверке §32, а не объявляются оптимальными заранее.

<a id="section-15"></a>

# 15. Corrective RAG на LangGraph

Обязательная последовательность сохраняется из `[RAG, «LangGraph-граф»]`:

```text
User Query
   ↓
Rewrite Query
   ↓
Retrieve: BM25 + vector → RRF
   ↓
Grade Chunks: каждый чанк relevant? yes/no
   ├── достаточно релевантных
   │      ↓
   │   Generate Answer → answer + sources
   └── недостаточно
          ↓
      Broaden Query
          ↓
      Retrieve снова — максимум 2 corrective-повтора
```

## 15.1 Узлы

`rewrite_query` переформулирует запрос для поиска, не теряя даты, числа, отрицания и ключевые сущности. `retrieve` выполняет оба поиска и объединяет ранги через RRF. `grade_chunks` использует локальную LLM для оценки каждого полученного чанка; один similarity threshold не заменяет этот шаг. `broaden_query` расширяет поисковую формулировку. `generate_answer` использует релевантный контекст и возвращает источники.

Ни один узел не дополняет историю пациента выдуманными сведениями и не обращается к внешнему AI API.

## 15.2 Повторы и недостаток данных

`retry_count` начинается с нуля. Принимаем явную трактовку задания: первоначальный retrieval плюс максимум два дополнительных поиска, то есть не более трёх retrieval-проходов.

Порог достаточности релевантного контекста задаётся конфигурацией и проверяется на корпусе. Письменное задание не задаёт его численно. После исчерпания повторов возвращается сообщение о недостаточности данных либо ограниченный ответ с обозначенными пробелами. Нельзя молча переключаться на общие знания модели или внешнюю LLM.

Технические повторы HTTP/LLM-запросов имеют собственный лимит и не считаются дополнительными corrective-циклами.

## 15.3 Проверяемость

Для синтетики доступна техническая трасса: исходный/переформулированные запросы, ID найденных чанков, grading yes/no, переходы, число повторов и использованные источники. Это наблюдаемые результаты работы, не требование раскрывать скрытые рассуждения модели.

Ссылки формируются из реально найденных документов и проверяются сервером. На реальных данных содержательные debug-логи по умолчанию выключены.

<a id="section-16"></a>

# 16. MCP-сервер

Обязательны четыре инструмента с исходными именами. Дополнительные инструменты в MVP не добавляются, однако запрет расширять API навсегда из задания не следует. `[RAG, «MCP-инструменты»]`

## 16.1 `index_folder`

Вход: путь к папке и glob-паттерн. Проектная форма аргументов:

```json
{"path": "./sample_docs", "glob": "**/*"}
```

Сканирует разрешённые файлы, разбивает на чанки, получает эмбеддинги, сохраняет ChromaDB, обновляет BM25 и metadata. Возвращает результат, счётчики и сведения о пропущенных/ошибочных файлах. Генеративная LLM и извлечение медицинских фактов не требуются и не вызываются.

`./sample_docs` — каталог внутри контейнера, заранее доступный после запуска. Внешнему MCP разрешён только этот синтетический корень; проверяются path traversal, нормализованный путь и выход через symlink. Нет возможности передать путь к личному архиву.

Повторная индексация неизменённых файлов не дублирует чанки.

## 16.2 `ask_question`

Вход:

```json
{"question": "Какой код указан в синтетическом отчёте о визите?"}
```

Запускает полный LangGraph. Возвращает читаемый текст ответа с источниками; structured output может иметь форму:

```json
{
  "answer": "В отчёте указан код SYN-CASE-7F29.",
  "sources": [
    {"source": "visits/visit-01.md", "chunkId": "demo-chunk-01", "position": 1}
  ]
}
```

Это образец контракта, не факт уже созданного корпуса. Ответ должен читаться host-агентом, а не состоять только из внутреннего ID фонового задания.

## 16.3 `find_relevant_docs`

Вход: запрос и `top_k`.

```json
{"query": "план повторного визита", "top_k": 5}
```

Возвращает ранжированные чанки с содержимым, источником и позицией после BM25 + vector → RRF. Не выполняет генерацию ответа, LLM-rewrite или LLM-grading: по таблице задания этому инструменту нужны BM25 и эмбеддинги, а не генеративная LLM.

## 16.4 `index_status`

Аргументов нет. Выход: число файлов, чанков и время последней индексации. До первого индексирования:

```json
{"files": 0, "chunks": 0, "lastIndexedAt": null}
```

Модели, включая embedding-модель, не вызываются.

## 16.5 Предметные descriptions

Письменное задание требует содержательных `description` инструментов; лекция подчёркивает также описание самого сервера `[ЛК-06]`.

Предлагаемый смысл server description/instructions:

> Сервер поиска по синтетическому медицинскому архиву Local Medical Archive. Используйте его для вопросов о визитах, документах, анализах, назначениях и проверочных фактах этого корпуса. Ответы основываются на локальных источниках. Сервер не предоставляет доступ к реальным медицинским данным пользователя и не является источником произвольных медицинских советов.

Descriptions четырёх tools объясняют разницу между индексированием, состоянием, поиском фрагментов и готовым ответом. Общей фразы «работа с документами» недостаточно.

На проверке host-агент получает предметный вопрос без инструкции «вызови MCP» и должен выбрать инструмент. Сохраняются фактический вызов и результат; документируется проверенная конфигурация host. Универсальная гарантия для любой внешней модели не заявляется.

## 16.6 Подключение

Основной способ проекта — локальный HTTP MCP endpoint. Лекция рекомендует HTTP, но не запрещает иные транспорты `[ЛК-08]`. Точный поддерживаемый режим, путь и конфиг проверяются на закреплённых версиях FastMCP и VSCode.

В репозитории обязательны готовый конфиг VSCode Copilot, порт/адрес и точная инструкция. Проверяющий не должен угадывать Docker exec-команду или настраивать транспорт самостоятельно. Дополнительно инструменты проверяются через MCP Inspector.

Опубликованный MCP работает только с `mcp_demo`; реальный корпус доступен лишь внутреннему API приложения. Переключателя на архив в публичном контракте нет.

<a id="section-18"></a>

# 18. External Consultation

## 18.1 Цель

Подготовить минимальный релевантный деперсонализированный медицинский контекст для ручной передачи внешней LLM.

## 18.2 Pipeline

```text
Question
   ↓
Relevant context selection
   ↓
Context minimization
   ↓
Rule-based de-identification
   ↓
Local LLM privacy pass
   ↓
Privacy warnings
   ↓
Preview
   ↓
Copy / Export Markdown
```

## 18.3 Удаляемые / заменяемые категории

Минимально:

- patient name;
- exact date of birth;
- phone;
- email;
- address;
- patient identifiers;
- insurance identifiers;
- doctor names;
- clinic names;
- document identifiers.

При необходимости:

- exact dates;
- geographical information.

## 18.4 Псевдонимизация

Примеры:

```text
John Smith → [PATIENT]
Dr. Smith → [DOCTOR_1]
Hospital X → [HOSPITAL_1]
47 years → age range 40–50
2025-03-12 → T-14 months
```

## 18.5 Privacy warnings

Система должна отдельно предупреждать о потенциальных quasi-identifiers.

Пример:

```text
Rare diagnosis retained
Exact age retained
Unusual surgical procedure retained
Small geographical region retained
```

## 18.6 Ограничения

MVP не заявляет математическую или юридическую гарантию полной анонимизации.

Результат следует считать деперсонализированным и минимизированным текстом, требующим ручной проверки.

## 18.7 Точность и граница экспорта

Очищается не только выбранный контекст, но и вопрос пользователя, заголовки и окончательно сгенерированный текст. Не экспортируются имена исходных файлов, PDF metadata, локальные пути, внутренние UUID/source refs и таблица замен. Выдаётся новый текст, а не изменённый оригинальный PDF.

В MVP достаточно одного сценария подготовки по вопросу, без конструктора сложных политик. Псевдонимы устойчивы внутри одного пакета. Даты можно представить как `T0` и интервалы; расчёт выполняется по сохранённым данным, а не приблизительно моделью. При неизвестной дате точный интервал не выдумывается. Числа, единицы, дозы, отрицания и порядок событий не меняются молча.

Экспортируемый текст должен совпадать с просмотренным и подтверждённым. После правки подтверждение сбрасывается. Неудачная проверка приватности означает предупреждение/ошибку и необходимость повторного просмотра, а не автоматический экспорт исходника. Редкие клинически важные сведения помечаются предупреждением; решение об их сохранении остаётся у пользователя.

# 23. Seed / demo data

## 23.1 Происхождение и готовность

Основной набор — синтетическая история одного вымышленного пациента. Открытые данные допускаются как дополнение при проверенных условиях использования, указании происхождения и отсутствии реальных персональных данных. Наличие файла в Интернете само по себе не считается разрешением включать его в Git.

В репозиторий входят готовые demo-данные; генератор при необходимости прилагается дополнительно. Преподавателю не нужно обращаться к внешней LLM, вручную вводить записи или искать датасет после запуска.

Синтетические документы явно маркируются. Их числа не выдаются за действительные медицинские рекомендации. Реальные документы пользователя, индексы и дампы в репозиторий не входят.

## 23.2 Прикладной seed собственного варианта

Принятый для проекта объём:

- не менее 30 медицинских записей суммарно; представлены PDF с текстовым слоем, транскрипты и заметки;
- история минимум за два календарных года и несколько типов документов;
- не менее 15 тегов;
- история исправлений минимум для 5 документов или фактов;
- связанные факты и события для timeline, фильтров и dashboard;
- реальные файлы синтетических оригиналов и корректные ссылки provenance для seed-фактов.

Числа 30, 15, 5 и два года — наши критерии собственного варианта, а не обязательные нормы всех full-stack заданий. Папки и wiki-связи из варианта 5 не добавляются.

Заранее подготовленные извлечения допустимы для быстрого наполнения demo, но маркируются как seed. Они не изображают только что выполненный inference. Новая загрузка и новый вопрос должны реально проходить локальный pipeline.

## 23.3 Корпус `sample_docs`

`[RAG]` требует не менее 500 КБ документов в комплекте и поддержки `.md`, `.txt`, `.py`, `.js`, `.ts`, `.json`, `.yaml`. PDF — дополнение, не замена этих форматов.

Проект принимает измеримую нижнюю границу `500 × 1024 = 512000` байт индексируемого содержимого. Это наша консервативная трактовка размера. Скрипт и manifest подтверждают объём: веса моделей, изображения без текста, служебный мусор и дубли ради размера не учитываются.

Помимо синтетических записей корпус содержит описание его структуры и терминов, чтобы можно было ответить на простые вопросы о содержимом архива. Вспомогательные файлы разных обязательных форматов индексируются как текст и не выполняются.

## 23.4 Проверочные факты

README содержит вопросы, ожидаемые необычные факты и точные исходные файлы. Факты находятся в самих документах, а не только в README и ожидаемом ответе теста. Эталонный файл ответов исключается из индексируемого корпуса.

Пример формы: «В синтетическом визите указан код SYN-CASE-7F29; повторный контроль рекомендован через 11 недель». До генерации набора это образец, а не уже существующий проверочный факт.

Для проекта принимается не менее 10 фактов разного вида: код, число, дата/интервал, деталь рекомендации. Задание не задаёт их количество; это наша проверочная граница. Все заявленные факты проверяются на настоящей выбранной локальной модели.

<a id="section-24"></a>

# 24. Прикладной seed и демонстрационный MCP-индекс

Full-stack после запуска должен содержать seed. При этом `[RAG, «Процесс сдачи»]` начинает проверку с пустого `index_status()`. Эти условия выполняются одновременно через два пространства данных одного поискового движка.

| Пространство | Назначение | Инициализация | Доступ |
|---|---|---|---|
| `archive` | Кабинет и Ask Archive | Seed автоматически; прикладной индекс готовится автоматически с видимым статусом | Внутренний API приложения |
| `mcp_demo` | Проверка четырёх MCP-инструментов | Пустое при первом чистом запуске | Опубликованный локальный MCP |

Сценарий на чистом demo-хранилище:

```text
index_status()                    → files=0, chunks=0, lastIndexedAt=null
index_folder("./sample_docs")     → индексирование синтетического корпуса
index_status()                    → files/chunks/lastIndexedAt
ask_question("...")               → ответ с источниками
find_relevant_docs("...", top_k=5) → ранжированные чанки
```

Обычный повторный запуск не обнуляет индекс. Для повторения проверки README описывает безопасный сброс только `mcp_demo`, а не удаление личных документов или всех Docker volumes пользователя.

Коллекции сами по себе не являются полной security-изоляцией. MCP-handler получает только разрешённый корпус, не принимает `corpus_id` от хоста и не умеет читать произвольные пути архива. Один код RAG используется обоими интерфейсами без двух независимых реализаций.

<a id="section-25"></a>

# 25. Приватность и безопасность

## 25.1 Защищаемая граница

Оригиналы, текст, факты, история, эмбеддинги и пакеты консультации остаются локальными чувствительными данными. Цель MVP — исключить автоматическую отправку архива и очевидные обходы ручного экспорта, а не заявить защиту от скомпрометированного хоста или полную анонимность.

Внешних LLM API, gateway, ключей frontier-провайдеров, web search и инструментов произвольного shell в приложении нет. Текст документов не должен попадать во внешнюю телеметрию и error-reporting.

## 25.2 Сеть и входные данные

UI без авторизации, Swagger и демонстрационный MCP публикуются по умолчанию только на loopback. БД и внутренний AI API не публикуются без необходимости. Это однопользовательское приложение для доверенного локального устройства, не публичный веб-сервис.

Рабочим сервисам ограничивается исходящий Интернет-доступ; для host Ollama разрешается явно заданное локальное соединение. Проверяется фактическая связность, а не только строка `internal: true` в Docker YAML. После подготовки UI, шрифты, PDF viewer и Swagger не должны требовать сторонних CDN.

Проверяются тип/размер загрузки, безопасное имя и серверный путь хранения. SQL-параметры валидируются и передаются через ORM. Markdown отображается без исполнения произвольного HTML/скриптов. PDF и текст считаются недоверенными данными: содержимое не получает права на новые tools, сетевую отправку или изменение конфигурации сервиса.

История хранится локально; содержательные тексты, таблицы замен и документы не печатаются целиком в обычные технические логи. Подробные диагностические traces допустимы на синтетике.

## 25.3 MCP не обходит ручной экспорт

При сдаче внешний host-агент может получить данные MCP. Поэтому опубликованный endpoint работает только с синтетическим корпусом. Реальный архив не подключается к внешнему Copilot/Claude или другому host-агенту как произвольно читаемая база.

Локальность модели внутри MCP не делает локальным дальнейшее использование ответа host-агентом. Проверяются запреты смены корпуса, path traversal и выхода через symlink. У публичных MCP-tools нет доступа к реальным источникам через аргументы.

Это граница доступа штатных API, не гарантия защиты от произвольного выполнения кода внутри всего AI-сервиса. Более строгая process/container-изоляция при такой модели угроз — отдельное последующее усиление, не скрытое обязательство текущего MVP.

## 25.4 Разработка и публикация

AI для разработки кода отделяется от AI работающего архива. В контекст coding-агентов, GitHub, CI, issue, screenshots и REPORT передаются только код, синтетические примеры и безопасные технические данные. Реальные медицинские документы, дампы и индексы исключаются из репозитория.

Для личного использования используются отдельные каталоги/volumes без demo seed. Это разделение сред, не multi-user. Публикация проверяется на секреты и настоящие персональные данные.

## 25.5 Подготовка и хранение

Первичная установка может загружать образы, библиотеки и веса. Этот этап не обрабатывает медицинские документы; downloader/init-компоненты не получают к ним доступ. После подготовки модели и приложение должны работать без внешних AI-сервисов и новых автоматических загрузок.

Шифрование диска ОС рекомендуется для личного применения. Собственное управление ключами, безопасные резервные копии и доказанное стирание копий остаются вне MVP. Нельзя заявлять, что Docker volume уже зашифрован либо soft delete гарантирует уничтожение данных.

# 28. Локальная LLM и конфигурация

## 28.1 Требования источников

`[RAG]` предусматривает небольшую локальную модель через Ollama. Указанные Phi-3-mini и Qwen2.5-3B — примеры, не единственные допустимые модели.

Лекция разрешает использовать Ollama на локальном хосте преподавателя вместо обязательного запуска внутри Docker; нужны точные модели и инструкция подготовки `[ЛК-05]`. Внешние AI API в работающем RAG не используются. Послабления третьей CAD-темы к этому проекту не относятся.

## 28.2 Проектный runtime

Сохраняется Ollama. Точная маленькая модель для сдачи выбирается после проверки extraction, grading и генерации на синтетике. Предпочитаемый пользователем более мощный локальный Qwen 3.8 остаётся настраиваемым вариантом; его наличие, тег и параметры не объявляются проверенными данным документом.

```text
LLM_PROVIDER=ollama
LLM_BASE_URL=<разрешённый локальный endpoint>
LLM_MODEL=<закреплённый после проверки тег>
EMBEDDING_PROVIDER=chroma_default или ollama
EMBEDDING_MODEL=<выбранная embedding-модель>
RAG_MAX_CORRECTIVE_RETRIES=2
```

Плейсхолдеры допустимы в спецификации, но перед сдачей стандартная конфигурация должна содержать конкретные работающие значения. Модель, endpoint, параметры поиска и лимиты не зашиваются в код.

## 28.3 Эмбеддинги

Базовое задание допускает встроенную модель ChromaDB. Переключаемая через конфиг embedding-модель Ollama — необязательное дополнительное задание. Для MVP достаточно одного проверенного локального provider; нельзя помечать переключение реализованным без теста.

Версия embedding-модели связана с версией индекса. При несовместимой смене требуется пересоздание, а не смешивание векторов. Веса подготавливаются до offline-работы; первый embedding-запрос не должен неожиданно требовать Интернет при обработке личного архива.

## 28.4 Фиксация после испытаний

В README и результатах evaluation фиксируются модель и digest/версия при доступности, параметры генерации, контекст, embedding-модель, версии зависимостей, ОС и CPU/RAM/GPU проверенной среды, фактическое время операций. Заранее не обещается скорость на любом компьютере или GPU-ускорение в любом контейнере.

# 29. Docker Compose и два режима Ollama

## 29.1 Стандартный all-in-one режим

Сохраняется команда письменных заданий:

```bash
git clone <repo>
cd <repo>
docker compose up
```

Компоненты: frontend, NestJS backend, PostgreSQL, Python AI/RAG-service и Ollama. ChromaDB in-process. Если требуется, модели автоматически подготавливает init/provisioning service; стандартный путь не требует ручного `ollama pull` и редактирования обязательных конфигов.

Миграции и идемпотентный demo seed выполняются автоматически. Прикладной индекс подготавливается с видимым статусом; `mcp_demo` остаётся пустым. Повторный запуск не перезаписывает пользовательские изменения и не дублирует seed.

На хост не требуется отдельно устанавливать Python, Node.js, Go или БД. GPU не является безусловным условием старта: для небольшой модели предусмотрен CPU-путь с честно указанными ограничениями.

## 29.2 Разрешённый лекцией host-Ollama режим

Приложение, БД и MCP работают в Compose; модель — в локальном Ollama преподавателя `[ЛК-05]`. README содержит отдельную точную команду/override и сведения о подготовке:

- модели и команды загрузки;
- адрес, по которому контейнер реально достигает хоста;
- проверка соединения, доступности модели и короткого запроса;
- особенности испытанных Windows/Docker/WSL или Linux-сред;
- отключение лишнего контейнера Ollama в этом режиме.

Не предполагается, что контейнерный `localhost` автоматически означает хост. Точная схема подключения проверяется, а не оставляется преподавателю для угадывания.

Это явно разрешённое лекцией исключение. Оно не заменяет упаковку остальных runtime-зависимостей в Docker и не требует другого локального inference-продукта.

## 29.3 Подготовка и готовность

Чистая установка может требовать Интернет для образов и весов. Это оговаривается отдельно от локальной работы с медицинскими данными. Никакие реальные документы не доступны компонентам скачивания.

README содержит реальные адреса UI/Swagger/MCP, состояния готовности и диагностические действия. `ready` не показывается, пока обязательный для операции компонент недоступен. После подготовки проверяется отсутствие внешних обращений при штатной работе; для host Ollama разрешено только локальное соединение.

# 30. Проверка в чистом окружении

Используется свежий clone в изолированной тестовой среде, без личной БД разработчика, старого индекса и прежних project volumes. Нельзя ради проверки удалять все Docker-данные пользователя на основном компьютере.

Проверяются сборка, миграции, seed, подготовка модели, health/readiness и порядок запуска. Затем открываются UI/Swagger, подключается MCP, обрабатывается новый документ и задаётся новый вопрос реальной модели.

Отдельно проходят стандартный all-in-one и разрешённый host-Ollama пути. После рестарта сохраняются данные и не дублируется seed. Сброс `mcp_demo` воспроизводит пустой статус, не затрагивая личный архив. Подготовленная среда проверяется без внешней сети.

README фиксирует реально испытанную ОС и конфигурацию. В лекции названы Windows и возможность проверки через WSL/Ubuntu; это целевой сценарий совместимости, а не доказательство уже проведённых нами испытаний `[ЛК-09]`.

# 32. Тестирование и проверка качества

## 32.1 Full-stack

`[FS]` требует не менее 10 unit/integration тестов. Наш отдельный набор покрывает создание заметки, upload, отклонение неверного файла, пагинацию, поиск/фильтры, изменение документа, soft delete, restore, исправление факта/историю, timeline и dashboard. Число тестов может быть больше минимального.

Проверяются обе стороны валидации и критические связи: удалённое не возвращается в поиске, исправление сохраняется при reprocess, оригинал выдаётся только через контролируемый маршрут.

## 32.2 RAG/MCP

`[RAG]` требует минимум 10 тестов, включая mock LLM unit-тесты графа, тесты индексатора и e2e MCP-инструментов. В проекте это отдельная группа минимум из 10. Суммарные 20 — наше правило прозрачного покрытия двух заданий, а не дословный единый минимум курса.

Покрываются все семь форматов, metadata чанков, повторное индексирование, BM25/vector/RRF, rewrite, grading, достаточный/недостаточный контекст, broaden, лимит повторов, ответ с источниками и четыре MCP-инструмента.

E2e MCP проходит через настоящий транспорт/клиент против сервера, а не только прямой вызов Python-функции. В детерминированных CI-проверках LLM/embeddings могут быть тестовыми адаптерами с явной маркировкой.

## 32.3 Настоящая маленькая модель

Mock-тесты не доказывают качество RAG. Перед сдачей выполняется отдельный прогон реального Ollama и настоящей embedding-модели. Лекция предусматривает перефразированные, простые и неожиданные вопросы, а также итерации над чанками `[ЛК-07]`.

Принимаемый проектом минимум — 20 оценочных вопросов, в том числе не менее 10 проверочных фактов. Это собственные численные критерии.

| Класс | Проверка |
|---|---|
| Точный факт | Необычное число, код, дата или деталь из документа |
| Перефразирование | Тот же смысл без дословного совпадения терминов |
| Обзорный вопрос | Что хранится в этом корпусе, как понимать его структуру |
| Несколько документов | Последовательность событий и рекомендаций |
| Даты/отрицания | Не потеряны условия, отрицания и даты событий |
| Отсутствие ответа | Система признаёт, что нужных данных нет |
| Противоречие | Различие источников показано, а не скрыто |
| Посторонний вопрос | Не создаётся выдуманный ответ от имени архива |

Каждый случай задаёт исходные документы, ожидаемые факты/допустимый отказ и ожидаемые ссылки. Эталоны хранятся вне индексируемого корпуса. Оценивается смысл и факты, не полное посимвольное совпадение.

Фиксируются наличие нужного источника в top-k, правильность фактов и ссылок, отказ при отсутствии данных, число corrective-повторов и фактическое время. Неудачи сохраняются, а не удаляются ради хороших цифр.

Все заявленные проверочные факты должны быть найдены с правильными источниками в финальном контрольном прогоне. Для остальных классов документируются результат и ограничения. Универсальный процент точности на любых медицинских вопросах не обещается.

Сравниваются как минимум две разумные конфигурации chunking/overlap; фиксируется, почему выбрана финальная. Это наш минимальный эксперимент по рекомендации лекции, а не дополнительный UI-модуль.

## 32.4 Host-агент

После подключения по готовому конфигу задаётся предметный вопрос без фразы «используй MCP». Фиксируются фактический выбор инструмента, вызов и ответ. Проверка только через Inspector этот сценарий не заменяет. Скрытые рассуждения модели не требуются.

## 32.5 Приватность на синтетике

Проверяются идентификаторы в документе, вопросе и имени файла; отсутствие локальных путей/таблицы замен в Markdown; сохранность чисел/интервалов; соответствие экспортированного и просмотренного текста; отсутствие отправки наружу; невозможность перейти demo MCP к реальному корпусу; недоверенные инструкции внутри документа.

Тестовый набор не доказывает полную анонимность; результат формулируется в пределах конкретных проверок.

## 32.6 Результаты

Команды находятся в README, случаи и конфигурации — в `eval/`, реальные машинные результаты — в `docs/evaluation/`. В них нет настоящих медицинских данных. Авторский разбор выполненных экспериментов добавляется лично в REPORT; результаты и опыт не сочиняются заранее.

# 33. CI

GitHub Actions подключается с первых рабочих изменений. Pipeline: lint → тесты frontend/backend/Python/MCP → сборка приложения и Docker-образов/проверка Compose.

В письменных общих требованиях Docker image build опционален, но в процессе проверки full-stack упомянуто «lint + тесты + сборка». Принимаем более строгий проектный вариант и включаем сборку, не выдавая это за одинаковую формулировку всех источников.

Обычный CI не требует API-ключей, GPU, персонального Ollama автора или медицинских данных. Детерминированные тесты используют mock/test adapters. Настоящий локальный evaluation — отдельная воспроизводимая проверка §32.3, а не подмена её тестовыми ответами.

Нельзя безусловно пропускать весь AI/MCP-набор, выдавать фиктивный зелёный результат или писать о реальном inference, который не выполнялся.

Рекомендуемый формат записи, не готовый личный отчёт:

```text
Дата / задача / commit
Что планировал сделать
Какой агент и модель реально использовались
Какой контекст и инструкции передал
Что получилось и что не получилось
Как проверил и что изменил
Ссылка на промпт/лог/результат
Открытый вопрос
```

AI может помочь шаблоном, извлечением фактических логов или помеченной редактурой, но не пишет от лица студента выдуманную историю работы. Вставка обозначается, например: «AI-фрагмент, модель/инструмент, дата, цель». Настоящих медицинских сведений в отчёте нет.

Эта спецификация подготовлена AI и не должна копироваться в REPORT как личный рассказ автора.

# 36. MVP acceptance criteria

Это план приёмки, не свидетельство уже работающей реализации.

Проект считается готовым, если выполняется весь следующий сценарий.

## Application

1. `docker compose up` запускает приложение.
2. Browser UI доступен.
3. Seed data уже присутствует.
4. Archive показывает документы.
5. Работают pagination, search и filters.
6. Можно создать note.
7. Можно загрузить text-based PDF.
8. Документ обрабатывается локальной LLM.
9. Видны summary и structured facts.
10. Fact показывает provenance.
11. Fact можно исправить.
12. Исправление видно в history.
13. Timeline отображает события.
14. Dashboard содержит статистику и график.
15. Ask Archive возвращает ответ с sources.
16. External Consultation создаёт sanitized preview.
17. Результат можно скопировать / экспортировать.
18. Swagger UI доступен.

## MCP / RAG

1. MCP подключается к host.
2. `index_status()` возвращает пустой индекс.
3. `index_folder("./sample_docs")` индексирует corpus.
4. Поддерживаются обязательные форматы.
5. `index_status()` показывает files/chunks.
6. `find_relevant_docs()` выполняет hybrid retrieval.
7. BM25 и vector results объединяются через RRF.
8. `ask_question()` запускает LangGraph.
9. Grade node оценивает chunks.
10. При недостатке контекста выполняется broaden + retry.
11. Retry ограничен двумя циклами.
12. Ответ содержит sources.
13. Host agent способен выбрать MCP tool по `description`.

## Process / quality / privacy

1. Есть реальный evaluation на выбранной маленькой модели, не только mock-тесты.
2. Не менее 10 проверочных фактов найдены с правильными источниками; остальные оценочные результаты и ограничения задокументированы.
3. REPORT написан автором по ходу работы, AI-вставки отмечены; ARCHITECTURE действительно предшествует коду.
4. Оба режима Ollama проверены по точным инструкциям.
5. Demo MCP не имеет API-пути к личному архиву, а экспорт содержит именно просмотренную версию без автоматической отправки.
6. Изменение/удаление документа не оставляет скрытую устаревшую выдачу; reprocess сохраняет ручные поправки.
7. Статусы выполнения критериев подтверждены командами, тестами и commit, а не только текстом спецификации.

# 42. Методология AI-разработки

## 42.1 Что подчёркивает лекция

Оцениваются организация работы с AI, контекст агентов, документация, продолжение свежей сессией, участие человека и проверка требований `[ЛК-02]`. Код предполагается генерировать AI в рамках выбранного процесса, а не просто предъявить результат одного промпта. Основной REPORT при этом пишет студент лично.

Следующий workflow — наш минимальный процесс, не дословно предписанная преподавателем методология. Конкретный coding harness выбирается при реализации; в отчёте называются фактически использованные инструменты.

## 42.2 Роли

Человек задаёт цель/ограничения, принимает архитектурные решения, проверяет diff и пользовательский результат, пишет личный журнал. Coding agent генерирует и исправляет код/тесты/техническую документацию. Проверять может тот же или отдельный агент, но окончательное принятие изменения остаётся за человеком.

Обычное исправление кода также поручается агенту. Фактические исключения не скрываются и при необходимости согласуются; нельзя заявлять полностью AI-сгенерированную работу, если процесс был другим.

## 42.3 Организация контекста

`PROJECT_SPECIFICATION.md` — что строим; `ARCHITECTURE.md` — устройство; `AGENTS.md` — правила и команды; `TASKS.md` — актуальная задача, проверка и следующий шаг. Значимые решения кратко фиксируются в `docs/decisions.md`.

Агент получает только относящиеся к задаче файлы и синтетические примеры. В инструкции закрепляются privacy boundary, обязательные четыре tools/форматы/граф, проверки и запрет подмены тестов выдуманными ответами. Личные медицинские документы не нужны для генерации кода.

## 42.4 Цикл задачи

1. Выбрать конкретное требование и критерий приёмки.
2. Передать агенту необходимые проектные документы, код и текущее состояние.
3. Получить небольшой план; проверить влияние на контракт, данные и приватность.
4. Сгенерировать реализацию и тесты.
5. Выполнить проверки, сохранить реальные ошибки и результат.
6. Провести ревью diff и сценария; исправить причину ошибки, а не только ожидаемый ответ теста.
7. Закоммитить осмысленное изменение, обновить состояние задач/решений.
8. Автор лично дополняет REPORT фактическим опытом работы.

Отдельный автоматизированный supervisor или orchestration framework не требуется. Достаточны ясные инструкции и небольшие проверяемые изменения.

## 42.5 Новая сессия агента

В конце сессии сохраняются текущая задача, принятые решения, изменённые файлы, выполненные команды и их результаты, известная ошибка и следующий шаг. Новый агент читает документы и handoff, затем сверяет их с Git и кодом.

Нельзя рассчитывать, что свежий агент помнит предыдущий чат. В handoff не включаются выдуманные выполненные действия и реальные медицинские данные. Контекст обновляется по факту изменений, а не накоплением бесконечной переписки.

## 42.6 Перед сдачей

Каждый пункт матриц §37–38 получает статус и доказательство. Независимый проход агентом полезен, но не заменяет человеческую проверку основных сценариев и clean-start.

В REPORT полезны настоящие примеры: неудачный chunking, потеря единиц, ошибка retries, неудачный tool description, восстановление контекста новой сессии. Такие истории включаются только если реально произошли.

### Собственный вариант: локальный медицинский архив с AI-каталогизацией, Corrective RAG и контролируемым деперсонализированным экспортом

- Новый публичный GitHub-репозиторий, ARCHITECTURE до кода, README, личный REPORT с методологией AI-разработки и маркировкой AI-вставок.
- Оригиналы не переписываются; реальные медицинские данные не включаются в demo/CI/репозиторий или контекст внешних кодинговых агентов.
- OCR, изображения, аудиотранскрипция, FHIR, multi-user и внешние LLM API вне MVP.

Отдельно — готовый RAG-корпус 500 КБ+ со всеми обязательными форматами и минимум 10 проверочными фактами в README.

**Оценочный набор проекта:** минимум 20 разнообразных вопросов к реальному RAG, ожидаемые факты и источники, фактические результаты и ограничения, проверка выбора MCP-инструмента host-агентом без подсказки.
