# Устойчивость результата: повторные реальные оценки

Один удачный прогон не доказывает воспроизводимость. Этот инструмент заранее объявляет всю серию, сохраняет каждую попытку и считает неуспехи, включая незавершённые запуски. Вопросы и полная метрика остаются штатными: текст + все ожидаемые источники + правильный отказ + privacy.

## Один запуск серии в Docker

Из корня репозитория, после установки Docker Compose. Python на хосте не нужен. Это отдельный стенд: нет PostgreSQL, личных документов, API/UI и опубликованных портов. Модели автоматически загружает init-контейнер, evaluator работает в internal-сети.

CPU:

```sh
docker compose -f compose.evaluation.yaml up -d --wait --wait-timeout 1800 ollama
docker compose -f compose.evaluation.yaml run --rm --build evaluator --execution cpu --output-dir /results/cpu-01
```

NVIDIA CUDA (требуется работающий доступ Docker к GPU):

```sh
docker compose -f compose.evaluation.yaml -f compose.evaluation.cuda.yaml up -d --wait --wait-timeout 1800 ollama
docker compose -f compose.evaluation.yaml -f compose.evaluation.cuda.yaml run --rm --build evaluator --execution gpu --output-dir /results/cuda-01
```

По умолчанию: **5 запусков на одном persistent-индексе + 3 запуска с новыми индексами**, все 21 вопрос, последовательно. Это 168 оценённых вопросов, а не выбор лучшего из восьми. `--same-index-runs` и `--fresh-index-runs` меняют числа только до начала серии; оба должны быть положительными. Не смешивайте CPU/CUDA в одной серии. Смена модели: установите `LLM_MODEL` для обеих Compose-команд, укажите новый output-dir.

Дефолт стенда — qwen3.5:2b, nomic-embed-text, Ollama 0.34.1, образ закреплён SHA256 manifest. `temperature=0`, `seed=42`, `think:false` для qwen3, один параллельный запрос. Контекст и token budgets сохранены для каждой операции. Один фиксированный синтетический warmup выполняется перед всей серией и не входит в счёт; затем `/api/ps` проверяет фактическое размещение обеих моделей на CPU/GPU. Не запускайте другие запросы к этой Ollama во время измерения.

Каждый полный прогон выполняется новым Python-процессом. В группе same-index используются сохранённые embeddings и одна папка индекса; штатный старт Corpus выполняет recovery: дописывает только отсутствующие векторы и удаляет orphan IDs, сохраняя существующие записи. Это проверка повторных запусков приложения на том же persistent-индексе, а не доказательство детерминизма одного неизменяемого HNSW-графа в памяти. В fresh-index каждому прогону выделена новая папка, embeddings и индекс строятся заново. Личные индексы не затрагиваются. Никакие каталоги автоматически не удаляются.

## Что читать в результате

Вывод `/results/cuda-01` появляется в `.local-evaluation/cuda-01` на хосте (игнорируется Git):

- `series.json`: план, окружение, все попытки и сводка отдельно по двум группам;
- `runs/same-01.json` и т. д.: полный результат каждого вопроса, ошибки, проверенные публичные payload;
- `profile.json`: fingerprint кода/промптов, корпуса, вопросов, lockfile, версии Python/библиотек, версии Ollama, digests обеих моделей, параметры генерации и поиска;
- `indexes/`: служебные индексы, **не добавлять в Git**.

В каждой группе есть все баллы, минимум/медиана/максимум, баллы первых десяти, частота PASS каждого вопроса и состояния `always-pass`, `always-fail`, `unstable`, `missing`. Незавершённые вопросы считаются неуспехами в знаменателе заранее объявленной серии. Прерванный эксперимент нельзя выдавать за успешную серию меньшего размера. Пустой/повторяющийся/переставленный набор результатов не может повысить оценку.

Код завершения: **0** — все запуски завершены и первые десять прошли во всех повторах; **2** — серия содержит незавершённые запуски или этот критерий не достигнут; **1** — ошибка настройки/окружения. `allQuestionsPassedEveryRun` отдельно показывает полное прохождение всех 21. Код 0 не обещает 21/21. Это фиксированное правило отчётности, не автоматическая аттестация преподавателем.

Отчёт обновляется атомарно после каждого вопроса/попытки. Существующий output-dir запрещён, в том числе после неудачи. Для новой попытки задайте новое имя; сохраните оба результата. Жёсткий timeout полного прогона задаёт `--timeout` (по умолчанию 3600 секунд). Его срабатывание остаётся в отчёте, следующие запланированные попытки выполняются.

## Повтор с тем же профилем

```sh
docker compose -f compose.evaluation.yaml -f compose.evaluation.cuda.yaml run --rm --build evaluator --execution gpu --profile /results/cuda-01/profile.json --output-dir /results/cuda-02
```

Несовпадение профиля блокирует оценку; перед каждым отдельным прогоном проверка выполняется снова. Не редактируйте код, корпус или параметры, пока идёт серия. Профиль первой серии фиксирует фактически установленное окружение, а не удостоверяет заранее выбранные эталонные веса: проверьте digests, затем используйте этот файл для последующих сравнений. CPU и GPU сравниваются отдельными сериями; аппаратные различия не становятся эквивалентными из-за одинакового seed.

## Поиск причины расхождения

Опциональная диагностика штатного evaluator (`--diagnostics`, включена серийным запуском) записывает **только SHA256**, типы операций и безопасные классы ошибок. Исходные запросы, ответы модели, внутренние цитаты и raw trace в диагностические поля не попадают; публичный MCP не изменён.

Сравниваются fingerprints переписанного запроса, поиска, грейдинга, выбранных источников, сырого ответа и проверенной выдачи. Для каждого вызова LLM/embeddings сохранены хеши входа и выхода. Если входы одинаковы, а выходы различаются — расхождение появляется у провайдера. Если найденные фрагменты различаются при одинаковых query/embedding-хешах — нужно исследовать индекс/ранжирование. Это локализация этапа, не окончательное доказательство причины. Случайный responseRef исключён из сравнения публичного ответа.

`stageVariants` показывает число различных состояний этапа в повторах одного вопроса. Одинаковый итоговый балл может скрывать разные проваленные вопросы; поэтому смотреть нужно и таблицу по вопросам. Устойчивый неправильный ответ — отдельная проблема качества, а не успех воспроизводимости.

Mock-тесты проверяют подсчёт и изоляцию инструмента. Только реальные сохранённые серии свидетельствуют о наблюдаемой устойчивости модели. Пять повторов не дают гарантии отсутствия редких ошибок.


## Читаемая сводка и сравнение этапов

После серии (также при её exit code 2) сформируйте Markdown-таблицу и сравнение первых различающихся вызовов, без новых запросов к модели:

```sh
docker compose -f compose.evaluation.yaml run --rm --no-deps --entrypoint python evaluator scripts/analyze_stability.py /results/cuda-01
```

В каталоге появятся `summary.md` и `analysis.json`. Для завершённой серии, пока индексы сохранены, анализатор дополнительно сравнит SHA256 сохранённых векторов каждого индекса. Сами векторы/индексы не экспортируются. На прерванной серии таблица явно помечена INCOMPLETE. Анализатор не меняет исходные отчёты или оценки.

`providerConsistency` дополнительно группирует все наблюдённые вызовы с одинаковыми хешами входа по каждому режиму и показывает, менялся ли хеш выхода/тип ошибки. Это наблюдательное сравнение уже выполненных вызовов, не отдельный эксперимент с принудительно замороженным контекстом.

`allRunChangedComparisons` сравнивает каждый прогон с самым первым, включая сравнение fresh-index с same-index. Отдельное `changedCaseComparisons` использует первый прогон своей группы. Так одинаковые результаты внутри групп не скрывают систематическое различие между ними.
