# Local Medical Archive — архитектура

Записано до создания прикладного кода, 2026-09-19. Основание: PROJECT_SPECIFICATION_Local_Medical_Archive_v1.1.md и два исходных задания. Это проект реализации, а не протокол пройденной приёмки.

## Границы и компоненты

Однопользовательский локальный архив. React + TypeScript + Vite отображает кабинет, архив, загрузку, документы/факты, timeline, Ask Archive, консультацию и историю. NestJS владеет REST API, PostgreSQL, оригиналами, неизменяемыми версиями текста, аудитом и устойчивой очередью обработки. ORM: TypeORM, явная начальная миграция. Python FastAPI/FastMCP предоставляет парсинг PDF, извлечение через Ollama и общий движок Corrective RAG на LangGraph. ChromaDB работает внутри Python; BM25 восстанавливается из того же сохранённого набора чанков. LangChain EnsembleRetriever объединяет ранги через RRF.

Нет OCR, внешних LLM API, отправки консультаций, авторизации и многопользовательского режима. API, UI и MCP публикуются на loopback. PostgreSQL и внутренний AI API не публикуются. Архив и MCP имеют разные корпуса и каталоги; MCP разрешён только синтетический sample_docs, без выбора корпуса и произвольных путей.

## Владение данными и целостность

Document хранит метаданные, статус, SHA256 и soft delete. TextRevision хранит исходный текст и страницы каждой версии. MedicalFact хранит значение, статус утверждения источника и отдельный reviewStatus. Provenance ссылается на конкретную версию, цитату и страницу. FactRevision и AuditEvent сохраняют изменения. ProcessingJob и ExtractionRun фиксируют обработку, версии модели/промпта/схемы и безопасные ошибки. Timeline использует медицинскую дату, которая может отсутствовать.

Редактирование текста исключает старую выдачу до переиндексации; удаление исключает документ из всех активных выборок. Правка метаданных, факта или восстановление из корзины ставят только переиндексацию, если последнее извлечение текущей версии текста завершено успешно; при незавершённой, упавшей или устаревшей обработке снова ставится полная обработка, поэтому извлечение фактов не теряется и FAILED не становится READY. Повторная обработка не перезаписывает проверенные пользователем факты. Если значение факта отличается от извлечённого из документа, reviewStatus всегда CORRECTED, даже при запросе CONFIRMED или UNREVIEWED: исправление пользователя не выдаётся за цитату источника. Коррекции индексируются с явной отметкой пользователя отдельно от исходных цитат. Оригинальные PDF не изменяются. Seed заранее подготовлен и честно маркирован, новые загрузки используют настоящую модель.

Консультация — локальный снимок минимального контекста. Правила и локальная LLM проверяют вопрос и весь пакет, удаляя идентификаторы. Неизвестные даты не придумываются; числа/дозы/отрицания сохраняются. Экспорт доступен только для текущего подтверждённого SHA256. Любая правка сбрасывает подтверждение. Внешний Markdown не содержит refs, путей и таблицы замен.

## Контракт между компонентами

Публичный API: /api; Swagger: /docs. Имена полей JSON — camelCase. Пагинация `{items,page,pageSize,total}`. Основные маршруты соответствуют §19 спецификации. Ошибка `{message,code?,statusCode}`. ID — UUID. Даты — ISO8601 или null. Document: `{id,title,documentType,documentDate,sourceType,status,summary,tags:string[],createdAt,updatedAt,deletedAt,text?,textVersion?,facts?}`. Списки документов принимают page/pageSize/q/type/tag/status/from/to/deleted/sort/order.

Внутренний Python API (порт 8001, заголовок X-Internal-Token, отдельный от MCP):
- POST /internal/parse: `{documentId,version,title,text?|filePath?}` → `{sourceIR,text,pages,warnings,parserVersion,parseRecipe}`; детерминированная стадия без вызова модели.
- POST /internal/process: `{documentId,version,title,text?|filePath?|sourceIR?}` → `{text,pages:[{pageNumber,text}],extraction:{documentType,documentDate,summary,tags,facts:[{type,name,valueText,valueNumber,unit,eventDate,assertionStatus,confidence,provenance:{page,sourceText}}]},warnings,model,promptVersion,schemaVersion,parserVersion}`.
- POST /internal/index: `{documentId,title,version,text,pages?,corrections?:[{id,name,valueText,valueNumber,unit,reviewStatus}]}` → статистика.
- POST /internal/remove: `{documentId}` → `{ok:true}`.
- POST /internal/ask: `{question,documentIds?:string[]}` → `{answer,sources:[{documentId?,source,chunkId,position,pageNumber?,text?}],trace?,insufficientContext?}`.
- POST /internal/consultation: `{question,contexts:[{text}]}` → `{content,warnings:string[]}`.
- GET /health → доступность процесса/моделей (без вызова генерации).

MCP Streamable HTTP /mcp на 8002: index_folder(path,glob), index_status(), find_relevant_docs(query,top_k), ask_question(question). Только mcp_demo. При чистом старте пуст. Shared uploads смонтированы read-only в AI. Python не имеет доступа к PostgreSQL.

## Уточнения по фактической интеграции (2026-09-19)

Docker Desktop 4.87 / Engine 29.7 не публикует порт контейнера, подключённого только к internal bridge: это обнаружено реальным HTTP-запросом. Добавлен отдельный ingress gateway. Только он публикует 8080/3000/8002 на loopback и подключён к ingress-сети; собственный OUTPUT firewall разрешает ему соединения только с frontend/backend/ai. Данные, Python и PostgreSQL остаются в internal-сети. Host Ollama proxy использует тот же firewall и разрешает только фиксированный host endpoint. NET_ADMIN выдан только этим двум сетевым прокси для настройки собственных правил; backend/AI/БД его не имеют. Так как авторизации нет, gateway отклоняет не-loopback Host (защита от DNS rebinding) и браузерный Origin, отличный от адреса самого gateway (защита от cross-site записи); для MCP допускается любой loopback Origin. Backend дублирует проверку для dev-запуска без gateway. Личный режим требует собственные `POSTGRES_PASSWORD` и `INTERNAL_API_TOKEN`: backend с `ARCHIVE_MODE=personal` не стартует с демо-значениями или значениями короче 16 символов.

При повторном запуске model-init проверяет наличие моделей локально через ollama show. Повторное скачивание уже подготовленных весов и обязательное обращение к registry не нужны.

## Историческая оценка модели v1.1

Параметры по умолчанию: chunk 900 символов, overlap 120, top-k 5, до двух корректирующих проходов (всего до трёх retrieval). Обе стратегии 900/120 и 1400/180 проверены на одном корпусе. Генерация ответа использует выбранные моделью точные цитаты; сервер проверяет, что каждая действительно содержится в доступном чанке. Цитата — один непрерывный фрагмент источника; отдельные строки принимаются, только если каждая совпадает с целой строкой источника и они идут в исходном порядке, и тогда показывается весь фрагмент между ними. Склеить несмежные куски в утверждение, которого нет в документе, нельзя. Это намеренно ограничивает свободный пересказ: небольшая модель при ранних испытаниях добавляла неподтверждённые сведения даже при корректно оформленных ссылках. Реальные ошибки и оценки сохранены отдельно от unit tests: промежуточный контроль 19/21; после ограничения генерации актуальный bounded-final-control.json — 17/21, первые 10 фактов 10/10. Падение общей метрики также зафиксировано, а не скрыто выбором удачного прогона.

Явный выбор документов консультации теперь определяет контекст напрямую (до восьми READY-источников), без генерации предварительного QA-ответа. Автоматический подбор сохраняет RAG. Проверки generation/textVersion выполняются перед privacy и после неё под блокировками БД; усечение исходного текста даёт предупреждение. Это устраняет отказ модели как препятствие для осознанного пользовательского выбора.

## Изменения v1.2 по конспекту консультации (2026-09-19)

Нормативный объём теперь определяет PROJECT_SPECIFICATION_Local_Medical_Archive_v1.2.md; происхождение и границы изменений перечислены в docs/CONSULTATION_CHANGES.md. Стек и продуктовые экраны сохранены. В корпусе нужны MD/TXT/текстовый PDF; Python, Chroma и пакет rank_bm25 остаются выбранной реализацией, а не отдельными ограничениями курса.

Один CorrectiveRAG обслуживает два фиксированных корпуса. Внутренний API сохраняет полную provenance для архива. Публичные ask_question и find_relevant_docs вызывают общий с ручной консультацией rules + local LLM sanitizer. Он проверяет все исходящие ответы и фрагменты; только подстановки идентификаторов допускаются после проверки медицинского содержания. Для MCP неоднозначность и сбой проверки закрывают выдачу фиксированной ошибкой без исходного текста. В ручной консультации неоднозначные числовые идентификаторы требуют пользовательской проверки; точный review hash остаётся обязательным.

Публичная схема источников содержит только reference S1/S2 и очищенный text. Непрозрачный responseRef позволяет локально сопоставить их с источниками в таблице public_references внутри mcp_demo/metadata.sqlite3. Инструмента получения этой таблицы в MCP нет. Имена файлов, исходные названия, пути, chunk/document IDs и trace исключены из публичного JSON. index_folder/index_status возвращают разрешённые агрегаты, skipped/errors — количества, без текстов и генеративной LLM. find_relevant_docs использует только retrieval и privacy, без rewrite/grading/генерации предметного ответа.

MCP передаёт очищенный результат подключённому host-агенту автоматически, поэтому граница ручного Copy/Markdown относится к личной консультации, а не ко всем данным системы. Публичный корпус остаётся только синтетическим mcp_demo. Внешние AI SDK, доступ к личному архиву и отправка консультаций не добавлены; nginx ingress и host-Ollama proxy по-прежнему решают локальные сетевые задачи.

Структурный splitter сохраняет целые абзацы, предложения, строки таблиц и пункты списков, когда они помещаются в лимит; overlap повторяет целые единицы. Для единицы длиннее лимита есть ограниченный fallback. Версия splitter входит в hash: следующий index_folder переиндексирует изменённые чанки и удалит ранее индексированные неподдерживаемые форматы. Сам startup генерацию/переиндексацию не запускает. Пользовательские исправления остаются помечены как не являющиеся цитатой оригинала.

Новый синтетический MCP-корпус: 42 файла, 663711 байт. В нём есть явно вымышленные ФИО, контакты и номер карты; контрольные факты описывают сроки, дозы, единицы, отрицания и неизвестность приёма. Старые RAG-метрики относятся к прежним вопросам и splitter. Новые результаты публикуются отдельно в docs/VALIDATION.md и docs/evaluation/v12-*.

## Устойчивость поиска при повторных оценках

При восстановлении Chroma из SQLite добавляются только отсутствующие content-addressed chunk IDs, а лишние удаляются. Повторный upsert уже подтверждённых векторов исключён: он мог менять HNSW-граф при обычном перезапуске. ID включает hash содержимого/версии/настроек, поэтому изменения источника получают новые ID; восстановление незавершённого удаления/обновления сохраняется.

Для небольшого MVP-корпуса запрос Chroma получает расстояния и ID всех подходящих чанков; сортировка `(distance, chunkId)` выполняется **до** отсечения dense-кандидатов. BM25 также использует явный tie-break по chunkId, список выбранных document IDs упорядочен. BM25/RRF и Chroma сохранены. Передача всех исходных текстов из Chroma не нужна — документы уже загружены из SQLite. Стоимость ранжирования растёт с размером корпуса; для больших архивов производительность требует отдельной проверки. Это сознательный выбор воспроизводимости для текущего объёма, не обещание масштабируемого ANN top-k.

Изменение проверяется отдельной серией после полной исходной серии, с теми же моделями и критериями. Hash-профиль кода различается; результаты не объединяются в один эксперимент.

## Дополнение: клинический обзор архива, 24 сентября 2026

Личный Ask использует отдельный LangGraph ArchiveRAG: отбор по разрешённым documentId и датам, BM25/dense/RRF, обзор доступных фрагментов в ограниченных пакетах, проверка точных цитат, повтор ошибочного пакета по одному источнику, хронологическая сборка. API передаёт снимок documentDate и версий; защита от удаления/редактирования во время генерации сохранена. Охват, пропуски индекса и непроверенные пакеты возвращаются явно. Публичный MCP сохраняет свой прежний CorrectiveRAG и privacy-контракт. Вопросы и ответы не записываются в содержательные серверные логи.


## Проектируемая подсистема обработки документов, 25 сентября 2026

**Будущее состояние, пока не реализовано.** [Medical Document Processing Pipeline](docs/MEDICAL_DOCUMENT_PIPELINE_PLAN.md) вводит общий неизменяемый IR: страницы/исходные spans → нормализация с картой происхождения → классификация/секции → проверенные аннотации. Из одной processing revision выводятся факты, provenance и специализированные чанки. Python выполняет обработку; NestJS/PostgreSQL владеет ревизией, очередью, review и указателем активного снимка. Новый микросервис не требуется.

Активация фактов и индекса использует подготовку новой версии и проверку manifests: распределённая транзакция PostgreSQL/Chroma не предполагается. Снимок чтения фиксирует processing и review revisions, исключая смешение версий. Старые parser/chunker и данные сохраняются до прохождения контрактных, crash/restart и реальных ingestion-проверок. Первый охват — LAB_REPORT и VISIT; parser-quality и extraction-quality проверяются отдельно от QA на предвычисленном seed.

[Следующие слои](docs/MEDICAL_KNOWLEDGE_PLAN.md): предметные structured tools, deterministic router, затем ограниченный локальный агент и отдельный справочный индекс. Личный архив, справочник и публичный синтетический MCP остаются разными пространствами; справочное утверждение не становится фактом пациента.

## Реализованная основа source IR, 25 сентября 2026

`/internal/process` дополнен опциональным `sourceIR` стадии `SOURCE_ONLY`: raw pages, UTF-8 spans, карта нормализации и два hash. Backend проверяет Python/TypeScript контракт и сохраняет неизменяемую запись `source_ir_revisions`, связанную с TextRevision. Идемпотентность по `(textRevisionId, irHash)`, UPDATE запрещён миграционным триггером; изменение страниц без изменения текста тоже создаёт новую TextRevision. Приватный `GET /api/documents/:id/source-ir` выдаёт IR текущей версии, legacy без IR возвращает 404. MCP не меняется.

Это пока источник для дальнейшего pipeline: extractor/chunker продолжают текущую обработку, независимые checkpoints и медицинские аннотации ещё не реализованы. [Фактический контракт и baseline](docs/evaluation/INGESTION_BASELINE.md).

## Стадия разбора до LLM и полный recipe (P1), 25 сентября 2026

Worker выполняет PROCESS в две стадии. Сначала `/internal/parse` строит `SOURCE_ONLY` IR без модели; backend проверяет IR и `parseRecipe` (версия recipe, parser, source IR, normalizer и hash) и одной транзакцией сохраняет TextRevision, запись `source_ir_revisions` с recipe и ссылку `processing_jobs.sourceIrRevisionId`. Затем `/internal/process` получает сохранённый IR, заново проверяет его целостность и принадлежность документу и только после этого вызывает extractor; повторного разбора оригинала нет. Результат должен быть проекцией того же IR (текст, `sourceHash`, `irHash`), иначе `SOURCE_IR_INVALID`.

`processingRecipe` описывает весь запуск: профиль и фактический путь (`lab`, `visit`, `visit-review`, `legacy`), parse recipe, модель и digest, параметры декодирования, версии аннотации/проекции/схемы фактов, лимит фактов и объявленные настройки индекса (chunker, размер, overlap, embedding и digest). Hash считается по тому же canonical JSON, что и IR; backend пересчитывает его и требует ссылку на hash сохранённой стадии разбора (`RECIPE_INVALID`). Значения recipe без float, чтобы Python и TypeScript сериализовали их одинаково. ExtractionRun хранит `sourceIrRevisionId` и `recipeHash`.

Повтор той же задачи после сбоя модели или перезапуска worker берёт сохранённую стадию и не разбирает оригинал снова; новая задача reprocess разбирает заново, одинаковый IR не дублируется. Миграция `ProcessingStages1753000000000` только добавляет nullable-колонки, прежние записи не переписываются. Это ещё не processing revision P3: активация facts/chunks одной ревизией и staging индекса не реализованы, настройки индекса в recipe объявлены AI-сервисом, а не подтверждены индексатором.

## Экспериментальный LAB annotator, 25 сентября 2026

`EXTRACTION_PROFILE=lab-rows-v1` строит типизированный лабораторный артефакт из source IR и проецирует его в факты. Backend проверяет source/hash/projection, сохраняет артефакт в ExtractionRun и выдаёт только актуальный результат в приватном document API. UI показывает исходные строки отдельно от review. Генеративной LLM в поддержанной LAB-ветке нет; другие документы сохраняют прежний extractor. Default legacy, MCP не меняется. Это не полная processing revision/activation система P3. [Контракт, серия и ограничения](docs/evaluation/lab-rows-v1/README.md).


## Постоянная история ручных консультаций

`GET /api/consultations` возвращает страницы сохранённых вопросов со статусом и количеством ответов, без raw contexts в списке. Приватный detail содержит проверенные версии и ответы. Явная миграция ConsultationHistory добавляет `consultation_prompts` и `consultation_responses`; подтверждение точного contentHash создаёт один неизменяемый снимок текста и sourceRefs. Повтор review того же hash идемпотентен. Старые текущие reviewed-версии переносятся при миграции.

`POST /api/consultations/:id/responses` принимает вручную вставленный ответ, название модели, promptId и client UUID. Составной FK запрещает связывать ответ с версией другой консультации. Повтор того же UUID/текста не дублирует ответ, другое содержимое даёт conflict. Снимки и ответы защищены от UPDATE триггерами. История не зависит от последующих правок текущего черновика; внешние ответы не участвуют в извлечении фактов, индексе или публичном MCP. В audit сохраняются ID/hash, без текста ответа.

## Резервная копия и восстановление, 25 сентября 2026

`scripts/archive_backup.py` работает на хосте через Docker Compose и не зависит от Python-пакетов проекта. `backup` останавливает писателей (`gateway`, `backend`, `ai`), выгружает PostgreSQL и тома `originals`/`ai_archive`, пересчитывает контрольные суммы после выгрузки и отказывается записать копию, если состояние изменилось; затем сервисы запускаются снова. Манифест содержит SHA-256 компонентов и файлов томов, число строк и хеш каждой таблицы, применённые миграции и хеши оригиналов из `documents`, без названий и медицинского текста. `restore` пишет только в пустой проект и сравнивает результат с манифестом. Синтетический `ai_demo` и веса Ollama не копируются: они восстанавливаются из `sample_docs` и повторной загрузкой.

## Целевая архитектура с локальным агентом, 25 сентября 2026

**Будущее состояние, пока не реализовано.** [Целевая архитектура](docs/TARGET_ARCHITECTURE.md): opencode с Qwen 3.8 27B в изолированном окружении без egress; отдельный Private Archive MCP поверх API backend (чтение по плану P5, запись только в виде предложений и выводов с review человеком); отдельный слой выводов агента, не смешанный с фактами пациента; справочная библиотека как skill; исследовательский цикл, где облачный запрос уходит и ответ возвращается только руками человека через существующую историю консультаций. Публичный MCP и его синтетический корпус не меняются.
